# A/B/C Prompt-Engineering Test — Parameter Over-Capture Regressions

Follow-up to the quote-escaping few-shot example added earlier this session
(`data/templates/function_parameters/function_parameters_main_template.txt`), which fixed
premature truncation on embedded double quotes (e.g. `Jo"seph` -> `Jo` became `Jo"seph` correctly)
but introduced three new "over-capture" regressions: the model grabbing more surrounding text than
the current parameter needed, in prompts with multiple clauses or multiple quoted fragments.

Three template variants were tested against the same fixtures used in `report_1`
(`claude/test_cases/multi_param_types`, `edge_values`, `ambiguous_and_adversarial`), scored the
same way (function name accuracy over 25 prompts with objective ground truth; parameter accuracy
over the resulting 63 parameters, counted only when the function itself was correct). All three
runs were clean -- no crashes, no stderr errors.

## The three configurations

- **Config A**: baseline (empty think-block + "no explanation" rule + quote-escaping rule/example,
  all already in place) **+ a new isolation rule only**: *"The request may describe multiple
  parameters at once -- extract only the part relevant to the current parameter, and never include
  text that belongs to another parameter or that is just narration."* No second example.
- **Config B**: baseline **+ a second few-shot example only**, no isolation rule. The new example
  demonstrates isolating one quoted fragment (`review`) out of a longer, multi-parameter sentence
  with other clauses before and after it (`Rate the gadget 'SuperWidget' 3 out of 5, review
  'Stopped working after a week', not great` -> `review:"Stopped working after a week",`).
- **Config C**: baseline + both the isolation rule and the second example together.

Backups of every template variant are under `claude/templates_backup_20260824-114838/`
(pre-session original) and `claude/templates_backup_20260824-114838/ab_test/` (the regressed
baseline this A/B/C round started from).

## Results

| Metric | `report_1` (original) | Regressed baseline (this session, before A/B/C) | Config A | Config B | Config C |
|---|---|---|---|---|---|
| Function name accuracy | 24/25 = 96% | 24/25 = 96% | 24/25 = 96% | 24/25 = 96% | 24/25 = 96% |
| Parameter accuracy | 58/63 = 92% | 59/63 = 94% | 59/63 = 94% | **61/63 = 97%** | **61/63 = 97%** |

Function-name accuracy is identical across every configuration -- the one recurring "miss" is
always the prompt-injection case, and in every run since the `<\|im_end\|>`/`<\|im_start\|>` guard was
added it's a clean refusal (`name: ""`) rather than a hijack, which the raw percentage doesn't
distinguish but is a materially better failure mode.

## Conclusions

1. **The isolation rule, alone, did nothing.** Config A is byte-for-byte identical to the
   regressed baseline on every case that mattered. A prose instruction competing against an
   already-demonstrated concrete pattern (the single-clause "copy everything" example) doesn't
   move this model's behavior on its own.
2. **The second example is what actually fixed the over-capture regressions.** Config B recovers
   both targeted cases (`review`, `message`) plus an unexpected third (`Reverse ''`'s empty
   string), for a net +3 correct parameters over the regressed baseline and +2 over the very
   first fix (report_1's 58/63).
3. **Adding the rule on top of the example changes nothing.** Config C is identical to Config B on
   every single case, confirming the rule is fully redundant once a concrete contrasting example
   exists.
4. **One new trade-off, isolated to a single case.** Both B and C reintroduce the
   `"empty string"`-literal bug on `"Greet the empty string \"\""` that had been fixed earlier this
   session. This looks like the same underlying class of problem as the deferred `''`-literal
   issue (the model has no precedent anywhere in the templates for what a correct, genuinely empty
   value looks like) -- worth addressing together as a follow-up, per the earlier decision to set
   the `''` case aside for later.

**Recommendation**: keep Config B's second example (the isolation rule can be dropped since it's
proven inert -- Config C offers no benefit over B for the extra template complexity). Net effect
versus `report_1`: parameter accuracy up from 92% to 97%, function name accuracy unchanged at 96%
with a qualitatively safer failure mode on the one remaining miss, at the cost of reintroducing one
known, already-understood empty-value bug to fix in the next round.

**Decision**: Config B was kept (isolation rule dropped, second example retained). The
`"Greet the empty string \"\""` regression is accepted for now, to be addressed together with the
deferred `''`-literal case in a later round.
