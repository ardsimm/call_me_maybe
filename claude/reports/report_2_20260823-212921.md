# Exception-Handling Gap Report — call_me_maybe

Follow-up to the docstring pass (which added NumPy-style `Raises` sections tracing exceptions
transitively through callees, not just what each function raises itself). Writing those sections
required tracing every call path end to end, and that surfaced several real gaps in how exceptions
are actually caught versus how the code's own `try`/`except` blocks suggest they should be. This
report collects them in one place, ranked by blast radius, with reachability noted for each: some
are proven crashes (confirmed by testing), others are structurally present but not currently
reachable given today's grammar/inputs.

## 1. `Context.__init__` exceptions escape `run()`'s catch (confirmed reachable)

`src/call_me_maybe.py`'s `run()` wraps `__get_context` in:

```python
except (ParsingValidationError, ParsingError) as e:
    print(f"Parsing failed: {e}")
    return
```

But `Context.__init__` (`src/models/context.py`) can raise several things that are neither:

- **`ValueError` from `ParameterType(value["type"])`** (`context.py:64`) when a parameter's
  `type` is outside the enum (e.g. `"array"`). **Confirmed by testing** — see
  `claude/reports/report_1_20260823-200910.md`'s `malformed_bad_parameter_type` case: real
  unhandled `ValueError` traceback on stderr, process still exits 0, no output file.
- **`TypeError`** if a parameter's definition isn't itself a dict — only the outer `parameters`
  dict is type-checked (`isinstance(parameters, dict)`), not each entry, so `value["type"]` on a
  non-dict entry raises directly.
- **`pydantic.ValidationError`** if `name`/`description` are empty strings — `Context` only checks
  `isinstance(name, str)`/`isinstance(description, str)`, never non-emptiness, but `Function`/
  `Parameter` enforce `min_length=1`. An empty string sails through `Context`'s manual checks and
  then fails at `Function(...)`/`Parameter(...)` construction instead.
- **`OSError`/`json.JSONDecodeError`** on a TOCTOU race: `Arguments.validate_model` already opened
  and validated both files once; `Context.__init__` opens and parses them again, moments later,
  from scratch. If either file changes or disappears in between, this raises directly (`context.py`
  uses raw `json.loads`, not `JSONAdapter`, and the `open()` calls have no surrounding `try` here).

All four reach `__main__.py`'s blanket `except Exception` instead of `run()`'s intended clean
message — see #3 for why that's worse than it sounds.

## 2. All-or-nothing batching (confirmed reachable, compounds #1 and #4)

`__process_prompts` (`src/call_me_maybe.py`) only catches `GenerationError` per prompt:

```python
for prompt in context.prompts:
    try:
        items.append(cls.__process_prompt(prompt, context))
    except GenerationError as err:
        ...
        continue
return items
```

Results accumulate in `items` and are written exactly once, via `__write_output`, after every
prompt has been processed. Any exception other than `GenerationError` raised mid-batch — anything
from #1, or a first-call model-load failure inside `GeneratorFactory.get_instance()` — discards
every result already generated for the entire run, not just the offending prompt. This is the same
failure shape as the two bugs already fixed this session (the `TokenizerFactory` arity mismatch and
the `parameter.valie` typo): one bad item anywhere in the batch loses everything.

## 3. `main()` never sets a non-zero exit code (confirmed reachable, the multiplier)

`src/__main__.py`:

```python
try:
    main()
except Exception as e:
    print("An unhandled error occured:\n", file=sys.stderr)
    print_exception(e)
```

No `sys.exit(1)`, no re-raise. Combined with #1 and #2, this means *any* unhandled exception —
proven (the `ParameterType` one) or latent (#4, #6) — looks identical to a successful run to
anything that only checks the exit code: exit 0, zero output file, only a traceback buried in
stderr to show for it. A moulinette/CI script checking exit status alone would report success on a
run that produced nothing.

## 4. Boolean branch raises the wrong exception type (latent, not currently reachable)

`__process_prompt` (`src/call_me_maybe.py`):

```python
elif parameter.type == ParameterType.BOOL:
    if parameter.value.lower() == "true":
        parsed_parameter = True
    elif parameter.value.lower() == "false":
        parsed_parameter = False
    else:
        raise ValueError(f"Invalid bool value {parameter.value}")
```

That `ValueError` is not a `GenerationError`, so `__process_prompts`' `except GenerationError`
would not catch it — it would hit #2/#3 same as anything else uncaught. Currently unreachable:
`generate_parameters` constrains boolean values to a trie built from exactly `"true"`/`"false"`
(`src/generate/__generator_impl.py`), so `parameter.value` can never be anything else. It's a trap
for the day that grammar changes and stops being airtight.

## 5. Two `except` clauses that can never fire, because they catch the wrong type (latent)

**`JSONAdapter`** (`src/adapter/__json_adapter.py`):

```python
def serialize(self, value: object) -> str:
    try:
        dump = json.dumps(value)
    except json.JSONDecodeError as e:
        raise SerializationException(e)
    return dump
```

`json.dumps` raises `TypeError` on a non-serializable value — never `JSONDecodeError` (that's a
*parsing* exception, not a serialization one). `SerializationException` can structurally never be
raised via this path. Not currently reachable in practice: everything ever passed to `serialize`
in this codebase (`List[OutputItem]`, plain str/dict/int/float/bool) is always JSON-serializable.

**`Arguments.validate_model`** (`src/models/arguments.py`) has the identical shape one level up:

```python
try:
    json_adapter.parse(functions_definitions.read())
except json.JSONDecodeError as e:
    raise ValueError(f"Invalid json format for file {self.input}: {e}")
```

`json_adapter.parse()` is `JSONAdapter.parse`, which already converts `json.JSONDecodeError` into
`DeserializationException` before it ever reaches `validate_model` — so this `except` clause is
dead code too. What actually propagates on malformed JSON is `DeserializationException`, not the
intended `ValueError`. This matters because pydantic only auto-wraps `ValueError`/`TypeError`/
`AssertionError` raised inside a `@model_validator` into `pydantic.ValidationError` — any other
exception type passes through the validator unwrapped. `DeserializationException` (via
`AdapterException(Exception)`) is such an "any other type", so it propagates raw out of
`Arguments()` construction, not as `ValidationError`.

Same file, same method: the `open()` calls sit *outside* the inner `try` entirely, so `OSError`
(e.g. the file was deleted) also propagates raw.

**Why this is currently harmless**: `ArgumentParser.parse` (`src/parsing/__argument_parser.py`)
wraps the whole `Arguments()` construction in its own blanket `except Exception as e: raise
ParsingError(...)`, which catches `DeserializationException`/`OSError` regardless of the intended
path being dead. Verified empirically — the `malformed_invalid_json` and `malformed_missing_file`
cases in `report_1` both produced the clean `"Parsing failed: ..."` message. So end-to-end behavior
is fine today, but only because of a second, wider net further out — the two-layer validation the
code appears to intend (`validate_model` catches JSON errors cleanly; `ArgumentParser` catches
validation errors cleanly) is really one non-functional layer riding on one working layer.

## 6. `StateFactory.get_instance`'s dead `TRIE_STATE` branch (latent)

`src/state/state_factory.py`:

```python
@staticmethod
def get_instance(type: StateType) -> State:
    if type == StateType.STRING_STATE:
        return StringState()
    if type == StateType.INT_STATE:
        return IntState()
    if type == StateType.FLOAT_STATE:
        return FloatState()
    if type == StateType.TRIE_STATE:
        return TrieState()
    raise ValueError(f"Invalid state type {type}")
```

`StateType` (`src/state/state_type.py`) has no `TRIE_STATE` member — only `FLOAT_STATE`,
`INT_STATE`, `STRING_STATE`. The `if type == StateType.TRIE_STATE` line is only ever reached once
the three real checks above it have failed, at which point evaluating `StateType.TRIE_STATE`
itself raises `AttributeError` (enum attribute lookup) — before the intended, clean `ValueError`
on the next line is ever reached. Not currently reachable: nothing in the codebase calls
`get_instance` with anything other than `STRING_STATE`/`INT_STATE`/`FLOAT_STATE` (trie states are
always built via the separate `get_trie_state_instance`). A landmine for a future caller who
reasonably expects `StateFactory.get_instance(StateType.TRIE_STATE)` to work, or who passes an
actually-invalid value expecting the documented `ValueError`.

## 7. `SystemExit` bypasses the app's own error messaging (minor, expected for `--help`)

`ArgumentParser.parse` (`src/parsing/__argument_parser.py`) calls `_ArgumentParser.parse_args`,
which calls `sys.exit()` directly on `--help` or an unrecognized argument. `SystemExit` is not an
`Exception` subclass, so `parse`'s own `except Exception as e: raise ParsingError(...)` never sees
it — the process exits via argparse's own usage/error text instead of anything from this codebase's
error-handling convention. Reasonable/expected for `--help`; less consistent for a genuinely
unrecognized flag, where the user gets argparse's raw message rather than a `"Parsing failed: ..."`
line like every other input problem in this project.

|---|---|---|---|
| 1 | `Context.__init__`'s `ValueError`/`TypeError`/`ValidationError`/`OSError` escape `run()`'s catch | `models/context.py`, `call_me_maybe.py` | **Yes** (confirmed) |
| 2 | Whole-batch loss on any non-`GenerationError` exception | `call_me_maybe.py` | **Yes** (confirmed, compounds #1) |
| 3 | Process always exits 0, even on crash | `__main__.py` | **Yes** (confirmed, masks #1/#2) |

| 5 | `JSONAdapter`/`Arguments.validate_model` `except` clauses catch the wrong exception type | `adapter/__json_adapter.py`, `models/arguments.py` | No (masked by a wider catch-all) |
| 6 | `StateFactory.get_instance`'s `TRIE_STATE` branch raises `AttributeError` not `ValueError` | `state/state_factory.py` | No (never called that way) |
| 7 | `SystemExit` from argparse bypasses app messaging | `parsing/__argument_parser.py` | Yes, but arguably correct for `--help` |

Suggested priority if addressing these: **1 -> 2 -> 3** together close the actual proven failure
mode (a bad input silently zeroing out a whole run's output). **5** and **6** are correctness/
clarity fixes for exception types that don't match their `except` clauses, lower urgency since
something further out already catches the fallout. **4** and **7** are cheap, defensive
one-liners worth doing opportunistically.
