# Report 7 - Performance audit: where the 14 minutes go

Date: 2026-08-31
Source: `out` (cProfile run at project root), plus fresh measurements on this machine.

## Summary

**100% of the runtime is `Small_LLM_Model.get_logits_from_input_ids`.** Nothing in
`src/` is slow. The constrainer, the trie, the states, the prompt building, the JSON
adapter and the pydantic validation together account for well under 1% of the wall clock.

So there are exactly two levers:

1. **Call the model fewer times** (fewer forward passes).
2. **Make each call cheaper** (shorter prompts -- cost is linear in prompt length).

Both are available and together they are worth roughly a 3x speedup, which is what is
needed to fit the subject's 5-minute budget.

Read off:

- `linear` is called 48856 times = 197 per forward pass = 28 layers x 7 projections +

  generated token**. The SDK exposes no KV cache, so this is structural.

## Why each call costs 2 seconds

The machine is an i7-12700, **CPU only** (no CUDA, no MPS), AVX2 only (no AVX-512, no AMX),
so `llm_sdk` runs the model in `float32` on 12 torch threads. There is no GPU to fall back to.

Measured cost of one `get_logits_from_input_ids` call against prompt length:

| prompt tokens | median ms |
|---|---|
| 100 | 1107 |
| 150 | 1774 |
| 250 | 2059 |
| 375 | 3734 |
| 500 | 5247 |
| 600 | 5239 |

That is essentially linear:

```
time_per_forward ~= 0.28 s + 0.0083 s x prompt_length
```

**Prompt tokens are the currency of this project.** Every token you add to a prompt costs
~8 ms on *every* forward pass of *every* token generated against that prompt.

Current prompt sizes (measured with the real fixtures, 12 functions):

| prompt | tokens |
|---|---|
| name selection | 375 |
| parameter (`fn_add_numbers`) | 587 |
| parameter (`fn_book_flight`, 5th param) | 634 |

## Finding 1 - one forward pass per completion is computed and thrown away

`src/generate/__generator_impl.py:85`:

```python
token = constrainer.pick_token(
    self.model.get_logits_from_input_ids(result)
)
```

Python evaluates the argument before the call, so the logits are always computed. But
`ConstrainerImpl.pick_token` starts with:

```python
allowed_tokens = self.state.get_allowed_tokens()
if allowed_tokens is None:
    return None
```

When the state signals end-of-generation, `pick_token` returns immediately and the
2-second forward pass that produced those logits is discarded. This happens **exactly once
per completion**.

The arithmetic confirms it precisely: the log contains 210 `Generated:` lines and the
profile shows 38 `__get_completion` calls and 248 forward passes. 210 + 38 = 248.

**38 of 248 forward passes -- 15.3% of total runtime -- are pure waste.**

Fix: ask the state whether it is finished *before* computing logits. Either have
`__get_next_token` check the constrainer's state first, or give `Constrainer` a
`is_done()` / `next_allowed()` accessor that `__get_completion` consults before calling
the model.

## Finding 2 - forced tokens are asked of the model anyway

`TrieState.get_allowed_tokens` returns `list(self.__current_node.keys())`. When that list
has exactly one element, the next token is **determined** -- the model's opinion cannot
change the outcome, since `max(allowed_tokens, key=logits.__getitem__)` over a one-element
list is that element whatever the logits say. Yet a full forward pass is run for it.

For the 12 names in the current fixture:

| name | tokens | forced |
|---|---|---|
| fn_add_numbers | 3 | 2 |
| fn_int_len | 3 | 2 |
| fn_float_len | 3 | 2 |
| fn_greet | 3 | 2 |
| fn_reverse_string | 3 | 2 |
| fn_get_square_root | 4 | 3 |
| fn_substitute_string_with_regex | 6 | 5 |
| fn_send_message | 3 | 2 |
| fn_control_lights | 4 | 2 |
| fn_control_temperature | 3 | 1 |
| fn_call_taxi | 4 | 3 |
| fn_book_flight | 3 | 2 |
| **total** | **42** | **28 (67%)** |

Two thirds of name-selection forward passes decide nothing. The same applies to boolean
parameters (`t` -> `rue` is forced) and to any single-token transition in `IntState` /
`FloatState` / `StringState`.

Fix: in the constrainer, if exactly one token is allowed, return it without touching the
model. This is not a heuristic and does not weaken the subject's "the function must be
chosen by the LLM" rule -- the choice is still made by the LLM at the branching tokens; it
is only the deterministic tail of an already-chosen path that is skipped.

Combined with Finding 1, name selection drops from ~55 forward passes to ~15 across
11 prompts: roughly 97 s -> 30 s.

## Finding 3 - the parameter prompt is twice the size it needs to be

`data/templates/function_parameters/function_parameters_main_template.txt` is 587 tokens,
broken down as:

| part | tokens |
|---|---|
| system header (the Rules block) | 137 |
| few-shot example 0 (`fn_add_number`) | 78 |
| few-shot example 1 (`fn_rate_product`) | 98 |
| few-shot example 2 (`fn_greet`) | 65 |
| few-shot example 3 (`fn_rate_product`) | 98 |
| the actual request | ~110 |

Three concrete cuts:

1. **Few-shot examples 1 and 3 are byte-identical.** The `fn_rate_product` /
   "Stopped working after a week" block appears twice. That is 98 tokens x ~8 ms x every
   forward pass of every parameter, for nothing. Deleting the duplicate is free.

2. **`Prompting.__context_prompt` is redundant.** `src/prompting/prompting.py:8` prepends a
   32-token `<|im_start|>system ... <|im_end|>` block to prompts whose templates *already*
   open with their own `<|im_start|>system` block. The model therefore sees two system
   messages with different instructions, at a cost of 32 tokens on every forward pass of
   the whole run.

3. **Four few-shot examples is more than this task needs.** Two well-chosen ones (one
   string with an escaped quote, one numeric) should hold accuracy while removing another
   ~160 tokens. This one needs an accuracy check before and after -- it is the only change
   in this report that can move correctness.

Cuts 1 and 2 alone: 587 -> 457 tokens (-22%). All three: 587 -> ~280 tokens (-52%), i.e.
5.15 s -> 2.35 s per forward pass, a **2.2x** speedup on the 75% of runtime spent in
parameter generation.

The name prompt (375 tokens) is mostly the 12 function descriptions, which are load-bearing
-- leave it alone apart from cut 2.

## Finding 4 - what is NOT worth optimising

For the record, so no time is wasted here:

- `logits.index(max(logits))` in the unconstrained branch is two Python passes over 151936
  floats: measured **9.8 ms**, i.e. ~1.5 s over the whole run (0.3%). `numpy.argmax` would
  fix it and numpy is allowed, but it buys nothing meaningful.
- `out.logits[0, -1].tolist()` plus the `[float(x) for x in logits]` comprehension inside
  the SDK: 3.5 s total (0.7%).
- The `print("Generated:", ...)` in `ConstrainerImpl.pick_token` (already removed in the
  working tree): a tokenizer decode per token, negligible.
- Trie construction, pydantic validation, template loading, JSON I/O: all below 0.1 s.

## Finding 5 - the structural ceiling

Even after all of the above, the design re-prefills the entire prompt for every generated
token. A 280-token prompt producing 12 tokens processes 3360 token-positions where a KV
cache would process 292 -- roughly **12x** more work than necessary.

This cannot be fixed through the SDK's public surface: `get_logits_from_input_ids` takes a
`list[int]` and returns logits, with no way to pass or receive `past_key_values`, and
`self._model` is a private attribute the subject forbids touching. Two thirds of the
`lm_head` work is wasted too (transformers computes logits for every position because
`logits_to_keep` defaults to 0), and that is equally out of reach.

Worth stating explicitly in the README's "Performance analysis" and "Challenges faced"
sections: the per-token full prefill is a constraint imposed by the provided SDK, and the
optimisation work consisted of minimising both the number of prefills and their length.

If the budget still is not met after Findings 1-3, the remaining lever is running prompts
in **parallel processes** (the subject's bonus list explicitly names "performance
optimizations (caching, batching)"). Caveats: each process loads its own ~2.4 GB of
float32 weights and this machine has ~7 GB free, so 2-3 workers maximum; torch already
uses 12 threads, so workers would need `torch.set_num_threads` lowered to avoid
oversubscription; and output ordering must be restored before writing the JSON array.

## Projected result

Starting from 45.2 s per prompt:

| change | effect | s/prompt |
|---|---|---|
| baseline | | 45.2 |
| Finding 1 (skip the discarded final forward) | -15% | 38.3 |
| Finding 2 (skip forced tokens) | name gen 97 s -> 30 s | 32.2 |
| Finding 3, cuts 1+2 (dup few-shot + context block) | param forwards -22% | 26.8 |
| Finding 3, cut 3 (4 shots -> 2) | param forwards -25% more | ~20 |

**~20 s per prompt, i.e. 20 prompts in ~6.5 minutes** -- a 2.3x improvement, still slightly
over budget. Getting comfortably under 5 minutes needs either a more aggressive trim of the
parameter prompt (the 137-token Rules block is the next target) or the parallel-process
option.

Recommended order of work: Finding 1, then Finding 2, then Finding 3 cuts 1 and 2 -- all
four are behaviour-preserving and cost nothing in accuracy. Measure. Only then touch the
few-shot examples, and re-measure accuracy alongside speed.
