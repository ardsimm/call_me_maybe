## 2. Blockers

### B1. `make lint` fails (exit 1)

The subject mandates the `lint` rule and its exact flags. It currently fails:

```
llm_sdk/llm_sdk/__init__.py:15: error: Unused "type: ignore" comment  [unused-ignore]
llm_sdk/llm_sdk/__init__.py:76: error: Unused "type: ignore" comment  [unused-ignore]
Found 2 errors in 1 file (checked 49 source files)
make: *** [Makefile:57: mypy] Error 1
```

The errors are inside the provided SDK, which must not be edited. `flake8` already excludes
`llm_sdk`; the `mypy` target does not.

Fix: add `--exclude llm_sdk` to the `mypy` target (Makefile:57). `mypy-strict` passes today only
because `--strict` happens to suppress these; exclude it there too for consistency.

### B2. `make debug` is broken

```
$ uv run python -m pdb src/__main__.py
ModuleNotFoundError: No module named 'src'
```

`python -m pdb <path>` sets `sys.path[0]` to `src/`, so the absolute `from src.call_me_maybe
import ...` cannot resolve. The subject requires a working `debug` rule.

Fix: `uv run python -m pdb -m src`. Verified working - it runs the full pipeline under pdb.

As a side benefit this also avoids `src/tokenize/` shadowing the stdlib `tokenize` module, which
`pdb` itself imports.

### B3. `src/` imports `torch` directly

```
src/tokenize/tokenizer.py:3:from torch import Tensor
src/tokenize/__default_tokenizer.py:2:from torch import Tensor
```

The subject: "The use of dspy (or any similar package) is completely forbidden including pytorch,
huggingface package, transformers, outlines, etc." `llm_sdk` using torch internally is fine - it
is the provided package. Your own code importing it is exactly what a reviewer greps for, and
these two lines are the only hits in the whole project.

Both are type annotations only. Fix: drop the annotation to something torch-free. The tokenizer
already only ever consumes the result via `.tolist()[0]`, so either return `List[int]` and adjust
the ~10 call sites, or annotate as `Any` if you want a zero-risk change before pushing. The first
is the honest fix and is also what the "recode the tokenizer" bonus is pointing at.

### B4. Uncaught crashes on malformed input files

The subject requires the program never to crash and to handle malformed input files gracefully.
Five input shapes produce an uncaught traceback and exit 1:

| Input | Result |
| --- | --- |
| `functions_definition.json` is a JSON object | `AttributeError: 'str' object has no attribute 'get'`, exit 1 |
| `functions_definition.json` is an array of strings | `AttributeError: 'str' object has no attribute 'get'`, exit 1 |
| prompts file is a JSON object | `AttributeError: 'str' object has no attribute 'get'`, exit 1 |
| prompts file is an array of strings | `AttributeError: 'str' object has no attribute 'get'`, exit 1 |
| prompts file is a bare scalar (`42`) | `TypeError: 'int' object is not iterable`, exit 1 |

Root cause: `Context.__init__` (`src/models/context.py:76` and `:129`) iterates whatever
`json.loads` returned and calls `.get()` on each element, without ever checking that the top level
is a list or that each element is a dict. `Arguments.validate_model` only checks that the files
are *parseable* JSON, not that they are the right shape, so nothing upstream catches this.

Two further gaps in the same function:
- the prompts file is opened at `:129` with no `try` around `open`/`json.loads`, unlike the
  functions file at `:78`.
- `ParameterType(value["type"])` assumes each parameter entry is a dict. This one is already
  caught (the `except TypeError` at `:124` converts it to a clean `ParsingError`) - the surrounding
  cases are not.

Fix: validate the top-level shape (`isinstance(x, list)`) and each element (`isinstance(el, dict)`)
before touching them, raising `ParsingError`; and wrap the prompts `open`/`json.loads` the same way
the functions file already is.

### B5. A function name that is a prefix of another makes the longer one unreachable

This is the most serious correctness bug, and the subject explicitly warns the input files will
change at review.

Given three functions `fn_get`, `fn_get_user_email`, `fn_send_email`:

```json
[
  {"prompt": "What is the email address of the user named alice?", "name": "fn_get", "parameters": {}},
  {"prompt": "Look up bob's email address",                       "name": "fn_get", "parameters": {}},
  {"prompt": "Get the counter value",                             "name": "fn_get", "parameters": {}}
]
```

`fn_get_user_email` can never be produced - 0% accuracy on any prompt needing it.

Root cause: `Trie.get_determinated_branch` (`src/trie/trie.py:64`). Its loop condition is
`curr_node.get(END_OF_BRANCH) is None`, so as soon as the walk reaches a node that terminates *a*
word, the loop body never executes and it returns `[quote_token]` immediately. `__get_completion`
(`src/generate/__generator_impl.py:155-162`) then appends that quote and `break`s. The shared
prefix always wins, and the continuation tokens sitting on the very same node are never offered to
the model.

Fix: in `get_determinated_branch`, return `None` when the node has real continuation children
alongside `END_OF_BRANCH` (i.e. children that are neither `END_OF_BRANCH` nor a
`string_end_sequences` token), so decoding continues and the model decides.

Note the coupled latent bug: `END_OF_BRANCH = -1` is stored as a key in the same dict as real token
ids, and `TrieState.get_allowed_tokens` returns `list(node.keys())` unfiltered. Today that is
unreachable precisely *because* the shortcut above always fires first. Fix the shortcut without
filtering `-1` out of `get_allowed_tokens` and `-1` becomes a selectable "token"
(`max(allowed, key=logits.__getitem__)` would happily index `logits[-1]`), which then gets appended
to the input ids. Fix both together.

## 3. Important, not blocking

### I1. Custom `--functions_definition` / `--input` still require the default files to exist

`ArgumentParser.parse` (`src/parsing/__argument_parser.py:67`) constructs `Arguments()` with its
defaults *before* applying the CLI overrides, and `Arguments.validate_model` opens and parses the
files on construction. So:

```
$ mv data/input/functions_definition.json /tmp/
$ uv run python -m src --functions_definition mine.json --input mine.json --output out.json
Parsing failed: Parsing error [Errno 2] No such file or directory: 'data/input/functions_definition.json'
```

Valid, existing, explicitly-passed files are rejected because unrelated defaults are missing. A
reviewer who points the tool at their own fixtures elsewhere hits this. Fix: apply the overrides
before validating - build the `Arguments` from the parsed values in one construction rather than
constructing-then-assigning.

### I2. The project needs Python 3.12+, but declares and documents 3.10+

`pyproject.toml` says `requires-python = ">=3.10"` and the README says "Python 3.10+". Two
language features push the real floor higher:

- `from enum import StrEnum` (`src/models/function.py:1`, `src/prompting/__templates.py:1`) -
  Python 3.11+.
- PEP 701 f-strings - multi-line expressions inside braces at `src/call_me_maybe.py:216` and
  `src/state/__trie_state.py:78`, and a nested same-quote expression at `src/call_me_maybe.py:245`
  (`f"[{item["parameters"][parameter.name]}]"`) - Python 3.12+.

On 3.10 or 3.11 this is an `ImportError`/`SyntaxError` at import time, not a runtime edge case. I
could not run it on those versions (only 3.13.1 is installed here), so this is from the language
version rules rather than an observed failure. Either raise `requires-python` to `>=3.12` and fix
the README, or rewrite those five lines and keep the 3.10 promise. The second is safer: you do not
know what the review machine runs.

### I3. Output filename does not match the subject's stated name

The subject contradicts itself: section V.4 says the program produces
`data/output/function_calling_results.json`, while the usage example on page 9 uses
`data/output/function_calls.json` (what the code defaults to). Since V.4 is the normative
"Output File Format" section and page 9 is only an example of passing `--output`, matching V.4 is
the lower-risk choice. Changing `Arguments.output`'s default costs one line.

### I4. Stray files committed

- `out` - a 200 KB captured stdout log of a previous run, tracked in git.
- `data.zip` - the original archive of `data/input/`, redundant with the extracted files.
- `data/templates/function_parameters/function_parameters_main_template.txt.bak` - byte-identical
  to the real template.

None break a rule, all make the tree look unfinished. Remove them (and add `*.bak` / `out` to
`.gitignore`).

### I5. The prompt-injection guard emits a schema-incomplete row

`CallMeMaybe.__process_prompt` (`src/call_me_maybe.py:206-210`) refuses outright any prompt
containing `<|im_end|>` or `<|im_start|>` and emits `{"prompt": ..., "name": "", "parameters": {}}`.

Two problems. First, `""` is not a name in `functions_definition.json`, so the row does not satisfy
"keys and types must match the schema exactly" and "all required arguments must be present" -
defensible as graceful degradation, but a reviewer may well not read it that way. Second, a prompt
containing that literal text is legitimate input (`Reverse the string '<|im_end|>'`) and is refused
rather than handled.

Escaping or stripping the special tokens from the user prompt before templating would defend the
same boundary without producing a row that fails the output contract. Same applies to the
`GenerationError` fallback in `__process_prompts` (`:263`), which emits the same empty shape.

## 4. Minor

1. `src/call_me_maybe.py:158` - `math.isinf(parsed_parameter)` on an `int` is dead code; a Python
   `int` is never infinite. Only the `float` branch at `:172` is meaningful.
2. `src/call_me_maybe.py:194` - the `BOOL` fallback assigns `""`, putting a string into a field
   declared `boolean`. Currently unreachable (the `TrieState` only permits `true`/`false`), but if
   it ever fires it emits a type-mismatched value. `False` is the safer fallback.
3. `src/models/arguments.py:74` - the error raised for a malformed *functions definition* file
   names `self.input`. Copy-paste; misleading message.
4. Missing docstrings, against the subject's PEP 257 requirement: `Trie.__init__`,
   `Trie.get_determinated_branch` (`src/trie/trie.py:19`, `:64`), `TrieState.trie`,
   `TrieState.current_node` (`src/state/__trie_state.py:84`, `:88`). Everything else in `src/` is
   documented - these four are the only gaps.
5. `src/generate/__generator_impl.py:152-164` - `token_count` is incremented after the second
   token, so the effective cap is 68, not `TOKEN_GEN_LIMIT = 67`.
6. `assert` is used for runtime invariants in `src/call_me_maybe.py:145`, `src/model/model.py:224`
   and `src/prompting/__templates.py:95`. These vanish under `python -O`. Raising is more honest.
7. `Arguments`' `min_length=6` on the three paths rejects a legitimate short path (`a.js`) with a
   confusing "String should have at least 6 characters". A path check would be more useful than a
   length check.
8. `StringStateStage.INITIAL = (0,)` / `DATA = (1,)` (`src/state/__string_state.py:4-6`) are tuples,
   presumably from a stray trailing comma. Harmless - enum values only need to be distinct - but it
   reads as a mistake. Same pattern at `src/prompting/__templates.py:11` and `:18`.

## 5. Test-suite gap

`make test` reports "Malformed-input robustness: 11/11", which is why B4 went unnoticed: every
fixture in `tests/test_cases/malformed_inputs/` keeps the top level as an array of objects and

array of scalars, bare scalar - have no fixture. Worth adding alongside the B4 fix, along with a
prefix-collision scenario for B5.
