### B5 in detail

The fix removed the `END_OF_BRANCH` sentinel and now infers "a word ends at this node" from the
presence of `string_end_sequences` children, then classifies each node by its continuation count:

| Node shape | Decision | Correct because |
| --- | --- | --- |
| 1 continuation, no word end | take it, keep walking | genuinely forced |
| >1 continuation | return None | real branch, model decides |
| 1 continuation + word end | return None | the prefix case - deciding here strands one name |
| 0 continuations | stop, close the string | word complete |

This is a better fix than the one report 9 proposed: dropping the sentinel means the `-1` can no
longer leak into the token ids at all, rather than being filtered out at each use site. The
coupled latent bug (`-1` reaching `logits.__getitem__` through `TrieState.get_allowed_tokens`) is
closed by construction, and `END_OF_BRANCH` is gone from the tree.

## 3. Accepted deviation: `torch` in `src/`

```
src/tokenize/tokenizer.py:3        from torch import Tensor
src/tokenize/__default_tokenizer.py:2  from torch import Tensor
```

Kept deliberately, on the reading that a type annotation is not "use of" the library. That is a
defensible position and the code does not touch a single torch API - `Tensor` appears only in
signatures, and every value is consumed via `.tolist()`.

It remains the one item in the project that a reviewer can point at and quote the subject back
("including pytorch"). Worth having the two-sentence answer ready at defence: the SDK's public
`encode` returns a `torch.Tensor`, so naming that type in a signature is unavoidable without
weakening the annotation to `Any`; no torch functionality is used. If a reviewer does not accept
it, the change is small - annotate as `Any`, or have `Tokenizer.encode` return `List[int]` and
adjust the call sites.

## 4. Why `accelerate` is required (answered)

It is not removable on this machine, and the chain is entirely inside the provided SDK:

1. `torch.cuda.is_available()` is `True` here (torch 2.12.0+cu130).
2. So the SDK's device auto-select picks `cuda` (`llm_sdk/__init__.py:47-48`).
3. Which makes it pass `device_map="auto"` to `from_pretrained` (`:72`, `device_map="auto" if
   self._device == "cuda" else None`).
4. transformers then calls `_get_device_map` (`modeling_utils.py:4288`), which lives in
   `transformers/integrations/accelerate.py` - a module importing `from accelerate import
   dispatch_model` and `from accelerate.utils.modeling import ...` at module scope (`:45-47`) -
   and expands `"auto"` through accelerate's `infer_auto_device_map` (`:365`).

On a CPU-only or Apple/MPS machine `device_map` is `None`, that whole path is skipped, and
accelerate is never imported. That is why it looked removable: it is genuinely optional there, and
mandatory on any CUDA box. Since the reviewer's hardware is unknown, keeping it is correct.

Note this also means the model loads through a different code path depending on the reviewer's
machine. Nothing in the project depends on which, but it is the reason a "works on mine" gap could
appear if accelerate were dropped.

## 5. Remaining items

### R1. Declared Python floor is wrong (the one real risk)

`pyproject.toml` says `requires-python = ">=3.10"` and `README.md:39` says "Python 3.10+". The code
needs **3.12**:

- `from enum import StrEnum` - 3.11+ - `src/models/function.py:1`, `src/prompting/__templates.py:1`
- PEP 701 f-strings - 3.12+ - multi-line expressions at `src/call_me_maybe.py:213` and
  `src/state/__trie_state.py:78`, nested same-quote expression at `src/call_me_maybe.py:242`

On 3.10 or 3.11 this is a `SyntaxError`/`ImportError` at import, not a runtime edge case. `uv sync`
honours `requires-python`, so a reviewer whose default interpreter is 3.11 gets a venv that cannot
run the project at all. Only 3.13.1 is installed here, so this is from the language version rules
rather than an observed failure.

Cheapest safe fix: set `requires-python = ">=3.12"` and update the README line. Rewriting the five
lines to stay 3.10-compatible is the alternative if you would rather widen support.
