# Code Audit — call_me_maybe

Quick audit of the codebase against design quality and the project subject's guidelines
(`private/en.subject.pdf`). Based on a full read of `src/`, the `Makefile`, `pyproject.toml`,
and a run of `make lint`, `make lint-strict`, and `black --check`.

## High severity (fix before submission)

### 1. Boolean parameters are always coerced to `True`

`src/call_me_maybe.py:73-74`

```python
elif parameter.type == ParameterType.BOOL:
    parsed_parameter = bool(parameter.value)
```

`parameter.value` is the *string* `"true"` or `"false"` (set at `__generator_impl.py:111`).
`bool("false")` is `True` in Python — any non-empty string is truthy. So no matter what the
model generates, every boolean parameter is serialized as `true`. This directly violates the
subject's "argument types must match the function definition" validation rule, and it fails
silently — nothing raises, nothing catches it. It needs a string comparison
(e.g. `parameter.value == "true"`), not a plain `bool()` cast.

### 2. `--functions_definition`/`--input` overrides skip validation entirely

`src/parsing/__argument_parser.py:36-45` + `src/models/arguments.py:21-41`

```python
arguments = Arguments()                       # validates the DEFAULT paths
parsed = parser.parse_args(source)
if parsed.input is not None:
    arguments.input = parsed.input             # plain attribute set, no re-validation
```

`Arguments()` with no kwargs runs `validate_model` against the hardcoded defaults
(`data/input/...`). The CLI overrides are then assigned as plain attributes afterward —
pydantic v2 doesn't re-run `model_validator` on assignment unless
`model_config = ConfigDict(validate_assignment=True)`, which isn't set. Net effect: the default
input files must always exist on disk even when you pass `--functions_definition`/`--input`,
and custom paths are never actually validated at this stage (only later, indirectly, when
`Context` opens them itself). This contradicts the documented usage pattern in the subject
(IV.3.2) where custom paths are the norm.

### 3. `make lint` currently fails (the subject's mandatory target)

```
src/model/model.py:4: error: Module "llm_sdk" has no attribute "Small_LLM_Model"  [attr-defined]
src/tokenize/__default_tokenizer.py:9: error: Returning Any from function declared to return "Tensor"
src/tokenize/__default_tokenizer.py:12: error: Returning Any from function declared to return "str"
```

Root cause: `mypy src ...` can't resolve the editable-installed `llm_sdk` workspace package
(hatchling's editable install uses an import-hook `.pth`, which mypy's static resolution
doesn't follow), so every `Model`-derived type collapses to `Any` and cascades into
`no-any-return` errors. Note `make lint-strict` (which runs `mypy .` over the whole tree,
including `llm_sdk/` as literal files) passes clean — so this is specifically a `src`-scoped
resolution gap, not a real type error. Subject says explicitly: "All functions must pass mypy
without errors" via the exact `lint` flags — this will get flagged in review as-is.

### 4. Likely Python 3.10/3.11 `SyntaxError`

`src/parsing/parser_exceptions.py:15`

```python
f"{'\n'.join([error.get('msg') for error in validation_errors])}"
```

A backslash inside an f-string expression (`'\n'` inside the `{...}`) only became legal with
PEP 701 in Python 3.12. `pyproject.toml` declares `requires-python = ">=3.10"` and the subject
mandates "Python 3.10 or later" — but this file will fail to even import on 3.10/3.11. Not
verified against a live 3.10/3.11 interpreter (none installed in this environment), but this is
documented CPython behavior, so treat it as a real risk rather than a confirmed non-issue.

## Design issues (not blocking, worth knowing about)

- **Global singleton sprawl instead of dependency injection**: `Model`, `AdapterFactory`,
  `TokenizerFactory`, `GeneratorFactory`, `PromptingTemplates` all hold private class-level
  singleton state (`__instance`, `__json_adapter_instance`, etc.), and `State.__init__`
  (`src/state/state.py:22-24`) reaches into `Model.get_instance()`/`TokenizerFactory.get_instance()`
  directly rather than receiving them. `Generator` and `Tokenizer`, by contrast, *do* take
  dependencies through the constructor. The two patterns coexist inconsistently, and the hidden
  global state makes the classes hard to unit-test in isolation (no way to reset/mock between
  tests without reaching into name-mangled private class attributes).
- **Duplicate file I/O and JSON parsing**: `Arguments.validate_model`
  (`src/models/arguments.py`) opens and parses both input files just to check they're valid
  JSON, then `Context.__init__` (`src/models/context.py`) opens and parses the *same* files
  again from scratch. Besides being wasteful, it's a minor TOCTOU gap (file could change between
  the two reads).
- **Unbounded generation loop**: `__get_completion` (`src/generate/__generator_impl.py:36-43`)
  loops `while token is not None` with no max-token safety cap. Every `State` is expected to
  eventually return `None`, but there's no circuit breaker if one doesn't (e.g. a future custom
  `State`, or pathologically long numeric input like the 30-digit test prompt in
  `function_calling_tests.json`). Given the subject's "under 5 minutes" performance requirement,
  a hard cap with a clear `GenerationError` would be a safer guarantee than trusting every state
  machine to terminate.
- **Function objects carry mutable generation scratch state**: `generate_parameters` sets
  `parameter.value = None` then mutates it in place on `Function.parameters`, which are the same
  shared objects stored in `Context.functions` and reused across every prompt
  (`src/call_me_maybe.py:51-52`). Currently harmless (value is always reset before use), but
  it's schema data doubling as per-call scratch space — a smell if this code is ever
  parallelized across prompts.
- **`Model` (singular, LLM wrapper) vs `models` (plural, pydantic schemas)** — easy to
  mis-click/mis-import between `src/model` and `src/models`; a rename (e.g. `llm_model`) would
  remove the ambiguity, though this is purely stylistic.

## Hygiene / minor

- `function_calls.json` (repo root) and `data/input/function_calling_tests.json.bak` are
  tracked in git — look like stray generated/backup artifacts that should be removed or
  gitignored.
- `make black` is not currently clean — `call_me_maybe.py`, `context.py`,
  `__generator_impl.py`, `__templates.py` and others would be reformatted. Not mandatory per the
  subject, but it's a Makefile target you advertise.
- No docstrings anywhere in `src/` yet — expected, since that's the next task, but it is one of
  the subject's General Rules (PEP 257 style), so worth flagging as a real compliance item, not
  just a nice-to-have.

## What's already solid

- Makefile matches the subject's required targets exactly (`install`, `run`, `debug`, `clean`,
  `flake8`, `mypy` with the exact mandated flags, `lint`, `mypy-strict`, `lint-strict`), plus
  `fclean`/`re`/`black` as extras.
- Function selection is genuinely LLM-driven via `TrieState`-constrained decoding — no
  heuristic/string-matching shortcut.
- Only public `llm_sdk` methods are used (`encode`, `decode`, `get_logits_from_input_ids`,
  `get_path_to_vocab_file`) — no private access.
- Resource handling is consistent: every file open goes through a `with` context manager.
- `IntState`/`FloatState`/`TrieState` genuinely restrict logits per JSON grammar (digits-only,
  decimal-point-forced, trie-walked function names) — the core "constrained decoding" claim
  holds for numeric and enum-like values.
