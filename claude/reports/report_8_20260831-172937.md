## Did each fix land?

**Fix 1 (don't compute logits when the state is finished) - yes.** `__get_next_token` is called
362 times but `get_logits_from_input_ids` only 325 times: **37 early returns, 37 forward passes
saved**, worth ~69 s. Note it fires on 37 of 58 completions, not all 58, because the other 21
(19 name completions plus 2 boolean parameters) now exit through the new trie shortcut instead.

**Fix 2 (skip forced trie tokens) - yes, and it is the biggest single win.** Name selection went
from 8.80 to 2.88 s/prompt, a 3.05x improvement. Only 40 forward passes now serve 19 name
completions - **2.1 per prompt, down from ~5.4** - which is the 67% forced-token saving showing up
exactly as predicted. Names remain correct in all 19 cases.

**Fix 3 (delete the duplicated few-shot) - yes.** The parameter template went from 4 few-shot
examples to 3; the duplicate `fn_rate_product` block is gone.

**Fix 4 (drop `Prompting.__context_prompt`) - yes.** Verified directly: rebuilding the name prompt
with the old block prepended gives 405 tokens against 372 now, **exactly the 33 tokens expected**.

Correction to report 7: that report quoted the name prompt as 375 tokens. The true baseline was
**405**. The 375 figure omitted the context block that `build_name_generation_prompt` was
prepending at the time. The parameter-prompt figures in report 7 were measured correctly.

## Corrected cost model

Report 7 gave `0.28 s + 0.0083 s x prompt_length`. That microbenchmark was taken while the machine
was loaded and is **~2.4x too high in absolute terms**. Re-measured on an idle machine, 7
repetitions per point:

| prompt tokens | 50 | 150 | 250 | 343 | 457 | 600 | 800 |
|---|---|---|---|---|---|---|---|
| ms | 236 | 545 | 941 | 1220 | 1632 | 2110 | 2836 |

```
time_per_forward ~= 0.063 s + 0.00347 s x prompt_length
```

This predicts the profile within 2%: name prompts at 372 tokens -> 1.35 s predicted, 1.370 s
measured; parameter prompts at ~490 tokens -> 1.76 s predicted, 1.868 s measured.

The **intercept is only 63 ms**, so ~96% of a parameter forward pass is prompt-length-driven. The
shape of report 7's conclusion survives its bad constants: prompt tokens are still the currency,
and now the exchange rate is known to be **3.47 ms per token per forward pass**.

## Where the remaining time is

**90.7% of the run is now parameter generation** (532.4 s of 587.2 s). Name selection is 9.3% and
is effectively solved.

Parameter generation is 285 forward passes for 39 parameters across 19 prompts - 7.3 forwards per
parameter, which is close to the floor (a value averages ~6.3 tokens plus one terminator, and
every one of those is a real model decision). **The forward count is nearly optimal; the cost per
forward is not.** Each of those 285 passes carries 408 tokens of fixed template (167-token header
plus 241 tokens of few-shot examples) to serve a 59-token live request.

At 3.47 ms/token, that fixed template costs **1.42 s of every 1.87 s forward pass**, i.e. ~400 s
of the 589 s run.

The parallel-process option from report 7 needs one correction: **max RSS measured 5.23 GB**, not
the ~2.4 GB of raw float32 weights I estimated (activations for a 500-token sequence, the
151936-float logits list, and torch's allocator account for the rest). With ~7 GB free on this
machine that is **2 workers, not 3**.

## One accuracy observation, not a regression claim

Prompt 9, "Tell my mom I'll be home in 42 minutes, then take me to 24 rue de la Paix", produced:

```json
{"name": "fn_send_message",
 "parameters": {"message": "I'll be home in 42 minutes, then take me to 24 rue de la Paix",
                "recipient": "John \"The Rock\" Doe"}}
```

`recipient` is wrong, and the value is copied **verbatim out of few-shot example 2**
(`Greet John "The Rock" Doe` -> `name:"John \"The Rock\" Doe"`). This is few-shot contamination:
the model reached into the demonstration instead of the request.

I cannot call this a regression - the baseline run log was overwritten before I could diff against
it (see below), so there is no before-picture. Flagging it because it lands directly on the next
piece of work: the few-shot examples are about to be cut, and this is evidence that the current
set is actively harmful on at least one prompt, not just expensive. Cutting to one short example
may fix this case as a side effect. Re-score `claude/test_cases/` either way.

Everything else in the 20 outputs is correct, including the 29- and 36-digit sums, the scientific
notation cases, `--42`, the escaped-quote names, `fn_book_flight`'s five mixed-type parameters,
and the prompt-injection refusal.
