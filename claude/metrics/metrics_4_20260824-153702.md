# Metrics — Scientific Notation Support in `FloatState`

Full report: `claude/reports/report_6_20260824-153702.md`. Same scope as `metrics_2`/`metrics_3`:
5 scenarios, 45 scoreable prompts / up to 102 parameters.

| Metric | Result |
|---|---|
| Function name accuracy | 44/45 = **98%** (unchanged) |
| Parameter accuracy | 100/102 = **98%** (up from 97%) |

`FloatState` gained real grammar support for scientific notation (`e`/`E`, a mandatory sign,
one-or-more exponent digits), closing the root cause behind the `Infinity`-overflow bug rather
than just containing its symptom. `"6.022e23"` now parses to the exactly correct `6.022e+23`
instead of a placeholder -- +1 parameter fixed, the only change from `metrics_3`. One bug caught
and fixed along the way: `plus_token` was initially assigned `encode("-")` (copy-paste of
`minus_token`) instead of `encode("+")`, making minus structurally the only legal choice after `e`
-- exactly matching the reported symptom ("Qwen always picks the minus sign after the e"). Verified
against 7 dedicated fixtures in `data/input/float_tests/` covering positive/negative exponents,
explicit/implicit signs, and the non-scientific case. One remaining, separate parameter miss in the
suite: a 52-digit number with no decimal point still overflows, tracing to a pre-existing,
unrelated gap (`PRE_FLOAT_POINT` has never allowed termination without first emitting a `.`).
