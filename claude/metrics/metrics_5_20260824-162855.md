# Metrics — Trailing/Embedded Minus-Sign Robustness (No Change to Scored Suite)

No new full-report accompanies this entry -- see the conversation record and
`claude/issues/issue_2_20260824-123805.md` (updated) for detail. Same scope as `metrics_2`-`4` for
the headline numbers, which are unchanged.

| Metric | Result |
|---|---|
| Function name accuracy | 44/45 = **98%** (unchanged) |
| Parameter accuracy | 100/102 = **98%** (unchanged) |

None of the 45 scored prompts happen to exercise the adversarial trailing/embedded-minus-sign
patterns from `issue_2` (a merged vocab token like `-",` smuggling a stray `-` past `IntState`'s
digit check), so this round's fixes don't move the headline numbers -- but they close a real gap.
`FloatState` gained a structural fix for the leading-minus position specifically: a new
`POST_MINUS_TOKEN` stage whose allowed tokens are digits only, so a merged token can never be
picked immediately after a leading `-`. A dedicated 17-case fixture,
`data/input/trailing_minus/` (leading/no-leading minus, single/double/trailing minus, embedded
mid-string minus, short and long digit runs, int and float, with and without decimals) came back
completely clean, including cases with far more digits than the original repro
(`"-123456789-"`) and embedded mid-string dashes (`"-4-2"`). `IntState`'s own code is unchanged
from when `issue_2` was found, so this robustness comes from the model's behavior under the
current prompt templates rather than an explicit code-level guarantee -- the same "defense via
model behavior, not a hard guard" pattern already noted for the prompt-injection guard. Marked
practically resolved in `issue_2`, not structurally closed.
