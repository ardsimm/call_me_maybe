# Template placeholder markers inside a user prompt get substituted with real values

`PromptingTemplates.get_next_function_parameter_template` runs `.replace()` over the **entire
accumulated prompt**, not just the fragment being appended:

```python
# src/prompting/__templates.py:375
return (
    (current_prompt + ungenerated_parameter_template)
    .replace("{[PARAMETER_NAME]}", next_parameter.name)
    .replace("{[PARAMETER_TYPE]}", ...)
    .replace("{[FUNCTION_NAME]}", function.name)
)
```

`current_prompt` already contains the user's text, so any placeholder marker sitting in that text
is substituted too.

## Measured

```
prompt : "Echo the text: {[PARAMETER_NAME]} and {[FUNCTION_NAME]}"
result : {"name": "fn_echo", "parameters": {"text": "text and fn_echo"}}
```

The user's literal text was rewritten into the parameter names and function name of the call
being generated. Pinned as the fourth case in `tests/test_cases/injection_variants/`.

## Severity

Low, and honestly so: a real prompt containing `{[PARAMETER_NAME]}` is vanishingly unlikely, and
the failure is data corruption in one string rather than a crash or a schema violation. It is
worth fixing mainly because it is a two-line change and because the same pattern is a hazard as
the template set grows -- this function is called once per parameter, so a prompt is rewritten N
times for an N-parameter function, and each pass can hit markers introduced by the previous one.

There is a related instance in `get_function_name_template`, where `{[FUNCTION_OPTIONS]}` is
substituted before `{[USER_PROMPT]}`. A *function description* containing `{[USER_PROMPT]}` would
therefore be filled with the user's prompt. Same class, same fix.

## Fix

Fill the fragment first, then concatenate -- so replacement only ever touches template text, never
text that came from the input files:

```python
fragment = (
    ungenerated_parameter_template
    .replace("{[PARAMETER_NAME]}", next_parameter.name)
    .replace("{[PARAMETER_TYPE]}", type_name)
    .replace("{[FUNCTION_NAME]}", function.name)
)
return current_prompt + fragment
```

The same discipline applies to the `generated_parameter_template` branch a few lines above, which
already gets this right (it fills the fragment before appending), and to
`get_function_name_template`, which should build `function_options` and substitute `{[USER_PROMPT]}`
into the *main template only* rather than into a string that already contains the options.
