# `torch` is imported directly in `src/`, which the subject forbids

> Subject IV.3.1, Additional Requirements: "The use of `dspy` (or any similar package) is
> completely forbidden **including pytorch**, huggingface package, transformers, outlines, etc."

Two files in `src/` import from torch:

```
$ grep -rn "^\s*\(import\|from\)\s\+torch" src/
src/tokenize/tokenizer.py:3:           from torch import Tensor
src/tokenize/__default_tokenizer.py:2: from torch import Tensor
```

Both use it only as a type annotation, mirroring the return type of
`Small_LLM_Model.encode(text: str) -> torch.Tensor`:

```python
# src/tokenize/tokenizer.py
@abstractmethod
def encode(self, data: str) -> Tensor:
    """Encode `data` into a tensor of token ids."""
```

## Why it should be fixed even though the intent is innocent

No torch *functionality* is used -- no tensors are constructed, no ops are called, nothing is
moved between devices. The import exists purely so the annotation can name the type the SDK
hands back. That is a genuinely defensible position, and it is worth being able to say it out
loud at the defense.

But the rule as written names pytorch outright, and the check a reviewer runs is
`grep -rn torch src/`, which returns two hits in the submitted source tree. Distinguishing
"imported for an annotation" from "imported for use" is a conversation you have to win rather
than one you get for free -- and the fix removes the need for that conversation entirely.

Note the distinction that *is* fine and should not be changed: `llm_sdk/` itself depends on
torch, transformers and huggingface-hub. That package is provided by the subject and copied in
verbatim ("To use `llm_sdk`, you can copy it in the same directory as the one `src` is in"), so
its dependencies are not the project's. The problem is only the direct import from the
project's own code.

## Fix

The clean version is not to swap `Tensor` for `Any`, but to stop leaking the SDK's return type
through the `Tokenizer` abstraction at all. `Tokenizer` exists precisely so the SDK can be
swapped out later (the subject's bonus track asks for rebuilding tokenization from
`get_logits_from_input_ids`/`get_path_to_vocab_file` alone) -- and an interface whose signature
names `torch.Tensor` cannot be implemented without torch, which defeats the point.

```python
# src/tokenize/tokenizer.py
@abstractmethod
def encode(self, data: str) -> List[int]:
    ...

# src/tokenize/__default_tokenizer.py
def encode(self, data: str) -> List[int]:
    ids: List[int] = self.model.encode(data).tolist()[0]
    return ids
```

This is a strict improvement beyond the compliance point. There are currently **11 call sites**
in `src/` spelling out the same unwrapping incantation:

```
$ grep -rn "\.encode(.*)\.tolist()\[0\]" src/ | wc -l
11
```

All eleven collapse to a plain `.encode(x)`, and the `.tolist()[0]` detail -- which is an
artifact of the SDK returning a 2-D batch tensor of batch size 1 -- stops being every caller's
problem. `Trie.__init__` also drops its `cast(int, ...)`.

Mind the one place the shape matters: `IntState`/`FloatState` build their digit token lists with
`reduce(lambda ac, el: ac + el, [...])` over per-character encodes, which stays correct with
`List[int]` and gets more readable.

## Checklist

- [ ] Change `Tokenizer.encode`'s return annotation from `Tensor` to `List[int]`
      (`src/tokenize/tokenizer.py`).
- [ ] Move the `.tolist()[0]` unwrapping into `DefaultTokenizer.encode`
      (`src/tokenize/__default_tokenizer.py`).
- [ ] Remove both `from torch import Tensor` imports.
- [ ] Simplify all 11 `.encode(...).tolist()[0]` call sites in `src/` to `.encode(...)`.
- [ ] Drop the now-unneeded `cast(int, ...)` in `Trie.__init__` (`src/trie/trie.py`).
- [ ] Verify `grep -rn torch src/` returns nothing.
- [ ] Re-run `make lint-strict` (mypy `--strict` currently passes; keep it that way) and
      `make test` to confirm no behaviour change.
