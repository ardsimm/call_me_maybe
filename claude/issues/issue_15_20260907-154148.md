# On CPU the 5-minute budget runs out at roughly 30 prompts

> Subject V.5, Performance and Reliability: "Reasonable speed: Process all test prompts in under
> **5 minutes** on standard hardware"

Measured on this machine (20 cores, CUDA available), default 11-prompt batch:

| Device | Elapsed | Per prompt |
|---|---|---|
| GPU (CUDA) | 11.9 s | ~1.1 s |
| CPU only (`CUDA_VISIBLE_DEVICES=""`) | 110.9 s | ~10.1 s |
| Full scenario set, GPU, 68 prompts | 121 s | ~1.8 s |

Peak RSS ~2.9 GB.

At ~10.1 s/prompt the 300-second budget is exhausted at **roughly 30 prompts**. The subject's
example `function_calling_tests.json` trails off with "...", so the reviewer's file length is
unknown, and a reviewer on a laptop has no CUDA device.

This is not a regression -- issue #5 already took the project from ~15 minutes to under 10 for
20 prompts, and the wins recorded there (skipping the discarded final forward pass, the trie's
forced-tail shortcut, trimming the templates) are all still in place and working. This issue is
about the remaining headroom and about being honest in the README.

## Where the time still goes

The structural cause is unchanged and is documented in issue #5: `get_logits_from_input_ids`
takes a `list[int]` and returns logits, with no way to pass or receive `past_key_values`. Every
generated token therefore re-prefills the entire prompt, making decoding O(n^2) in prompt length.
The SDK exposes no KV cache and `self._model` is a private attribute the subject forbids
touching, so this ceiling is not reachable through the permitted surface.

That leaves prompt length as the lever, and the parameter prompt is where the length is:

- `templates/function_parameters/function_parameters_main_template.txt` still carries **three
  full few-shot examples** plus a ~137-token Rules block.
- It is re-tokenized from scratch for **every parameter of every prompt** -- so a 5-parameter
  function like `fn_book_flight` pays for it five times.
- Each parameter's prompt also appends every previously generated parameter, so the prompt grows
  monotonically within a single function call.

Issue #5's last open item -- "trim the few-shot examples from 4 to 2" -- was partially done (4 to
3) and is the obvious next step. Its checklist notes the caveat: this is the one change that can
move accuracy, so it must be measured against `make test`, not just the clock.

## The cheaper structural win

Beyond trimming, the tokenized prefix of the parameter template is **identical across every
parameter of every prompt** -- only the tail differs. Encoding it once and reusing the token list,
rather than re-encoding the whole string each time, removes a per-parameter tokenization pass.
That is pure bookkeeping with no accuracy risk, and it is explicitly on the subject's bonus list:

> Bonus Part: "Performance optimizations (caching, batching)"

## What the README should say

The README's "Performance analysis" section now carries the CPU number and the ~30-prompt
ceiling, added while fixing the stale figures. What it does not yet explain is *why* -- the
per-token full prefill and the unreachable KV cache. Issue #5's checklist has that as an open
item and it is still worth doing: "the SDK gives us no KV cache, so we minimised the number of
prefills and their length instead" is a much better answer at a defense than a bare timing table.
