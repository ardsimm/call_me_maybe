# Only `\"` is unescaped, so backslashes are doubled and `\n`/`\t` come out literal

`GeneratorImpl.__handle_escaped_quotes` is the entire un-escaping step:

```python
# src/generate/__generator_impl.py:85
def __handle_escaped_quotes(self, completion: str) -> str:
    return completion.replace('\\"', '"')
```

The model is instructed by the prompt template to emit JSON-escaped text, and it obliges -- for
backslashes, newlines and tabs as well as quotes. Everything except `\"` is then left as two
literal characters and re-escaped by `json.dumps` on the way out, so it comes back doubled.

## Measured

From the new `tests/test_cases/string_round_trip/` scenario:

| Prompt asks for | Output contains |
|---|---|
| `C:\Users\admin\Documents\report.txt` | `C:\\Users\\admin\\Documents\\report.txt` |
| `a backslash \ on its own` | `\\` -- the rest of the sentence is lost |
| a real newline inside the value | literal `\n`, two characters |
| `{"a": 1, "b": [2, 3]}` | `{` |
| `he said "stop" and then left` | correct |

Raw JSON, so the doubling is unambiguous:

```json
{"prompt": "Echo the text: C:\\Users\\admin\\path",
 "name": "fn_echo",
 "parameters": {"text": "C:\\\\Users\\\\admin\\\\path"}}
```

Only the `\"` case survives, and it survives because
`templates/function_parameters/function_parameters_main_template.txt` contains a few-shot example
teaching exactly that one escape:

```
name:"John \"The Rock\" Doe",
```

Scenario score: 3/8 parameters correct, with all 5 failures traceable to this function.

## Fix

Replace the single `.replace()` with a real JSON string decode. The generated text is already a
JSON string body -- that is the whole termination convention -- so wrapping it in quotes and
handing it to `json.loads` decodes every escape sequence correctly in one step:

```python
def __decode_json_string(self, completion: str) -> str:
    """Decode a generated value as a JSON string body.

    Every value is generated as if it were the inside of a quoted JSON
    string, so the model emits `\\"`, `\\\\`, `\\n`, `\\t` and `\\uXXXX`
    escapes. Decoding them here is what makes the value round-trip; a
    malformed escape falls back to the raw text rather than failing the
    prompt.
    """
    try:
        decoded = json.loads(f'"{completion}"')
        return decoded if isinstance(decoded, str) else completion
    except json.JSONDecodeError:
        return completion
```

The fallback matters: the model can emit a trailing lone backslash or an incomplete `\u` escape,
and a `GenerationError` there would lose the whole prompt over a cosmetic problem. Returning the
raw text is no worse than today's behaviour.

Note this is the project's own `JSONAdapter.parse` in spirit -- and that method currently has no
callers at all (issue #20), so this is a chance to give it one, or to delete it knowingly.

## What this does *not* fix

The `{"a": 1, "b": [2, 3]}` -> `{` case is a different problem and should stay documented as a
limitation. `Model.string_end_sequences` decides a string has ended by looking at whether the
*token's own text* contains an unescaped `"`, with no knowledge of the string built so far. When
the model emits an unescaped quote mid-value -- which it does whenever the value itself is
JSON-shaped, few-shot example notwithstanding -- the value is cut there.

The README's "Challenges faced" section already names this design choice as "the root cause
behind most of the issues below", which is accurate. Fixing it properly means tracking escape
state across tokens inside `StringState` rather than treating termination as a per-token
property, which is a real redesign. Worth stating as a known limitation rather than attempting
under time pressure.
