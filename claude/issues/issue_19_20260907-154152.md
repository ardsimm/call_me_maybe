# A missing prompts file reports "Error while parsing functions definition"

`CallMeMaybe.__get_context` opens both input files inside one `try`, and the handler names only
the first:

```python
# src/call_me_maybe.py:176-186
try:
    with (
        open(arguments.functions_definition) as functions_definition,
        open(arguments.input) as prompts,
    ):
        functions_json = functions_definition.read()
        prompts_json = prompts.read()
except (OSError, json.JSONDecodeError) as err:
    raise ParsingError(
        f"Error while parsing functions definition:\n{err}"
    )
```

So every file-level failure is attributed to the functions file:

```
$ uv run python -m src --functions_definition ok.json --input /does/not/exist.json
Parsing failed: Error while parsing functions definition:
[Errno 2] No such file or directory: '/does/not/exist.json'
```

The message says "functions definition"; the file that failed is the prompts file. The `errno`
line underneath does name the right path, so the information is recoverable -- but the sentence
above it actively points the reader at the wrong file.

## The rule

> Subject IV.3.1: "All errors should be handled gracefully. Your program must never crash
> unexpectedly and must always provide **clear error messages** to the user."

The handling is graceful -- exit 0, no traceback, no partial output. Only the wording is wrong.

Same pattern one block down, where both files are decoded and validated together:

```python
except ValueError as e:
    raise ParsingError(f"Failed to parse JSON input: {e}")
```

Here it is less severe, because pydantic's own error text names the offending path
(`functions.0.parameters.a.description`), so the reader can tell which file it came from. Still
worth saying which file is which.

## Fix

Cheapest correct version -- use the exception's own filename, which `OSError` already carries:

```python
except OSError as err:
    raise ParsingError(f"Could not read input file {err.filename}: {err.strerror}")
```

Cleaner version -- open the two files separately so each has its own message. That also fixes a
second small thing: a `json.JSONDecodeError` can never be raised by this block, since nothing in
it parses JSON (decoding happens below via `pydantic_core.from_json`, which raises `ValueError`).
The `json.JSONDecodeError` in the tuple is dead (see issue #20).

```python
functions_json = cls.__read_file(arguments.functions_definition, "functions definition")
prompts_json = cls.__read_file(arguments.input, "prompts")
```

Note that separate `open()` calls lose the single-`with` guarantee that both handles close
together, which is trivially fine here -- each file is read fully and closed before the next is
opened, and the subject's resource-management requirement (IV.1) is satisfied either way as long
as both use context managers.

- [ ] Drop `json.JSONDecodeError` from that `except` tuple -- nothing in the block can raise it.
- [ ] Name the file in the `ValueError` handler below it too, so
      `Failed to parse JSON input` says which input.
