# Numeric overflow produces invalid JSON, and the prompt-injection guard is trivially bypassed

Found while expanding the test suite (`claude/test_cases/new_functions`,
`extreme_edge_cases`, `injection_guard_robustness`) -- full detail and reproduction traces in
`claude/reports/report_4_20260824-125422.md`.

## Checklist

- [x] **A numeric parameter can overflow to `Infinity`/`-Infinity` and still pass validation,
      producing invalid JSON.** `"What is the sum of 6.022e23 and 1"` ->
      `{"a": 6.022, "b": Infinity}`. `Infinity` is not valid JSON (disallowed by RFC 8259), which
      contradicts the "100% valid JSON, always" guarantee. Root cause: for parameter `b`, the model
      generates `1` followed by 500 consecutive `0` tokens, hitting `GeneratorImpl.TOKEN_GEN_LIMIT`
      (the safety net does prevent a hang, so that part works as intended). But
      `float("1" + "0" * 500)` doesn't raise `ValueError` in Python -- it silently overflows to
      `inf`. `generate_parameters`'s validity check only catches `ValueError`, so the
      overflowing-but-syntactically-valid numeral sails through untouched, and
      `json.dumps(float('inf'))` emits the literal non-standard token `Infinity`.
      **Fixed**: `call_me_maybe.py` now checks `math.isinf(parsed_parameter)` per numeric
      parameter and, on overflow, replaces only that parameter with a type-correct placeholder
      (`42`/`42.0`) instead of raising -- the function name and every other parameter still come
      through normally, rather than the whole prompt refusing. (An earlier revision of this fix
      made the entire prompt refuse instead; this version is more useful since a caller still gets
      a function to call.) Verified in `claude/reports/report_5_20260824-135103.md`'s post-fix
      re-run: valid JSON, correctly typed, no crash. The underlying scientific-notation grammar gap
      below is what triggers this and is still open.
- [x] **`FloatState` has no grammar support for scientific notation** (`e`/`E`/`+` are not in its
      allowed tokens at all, `src/state/__float_state.py`), so a source value like `6.022e23`
      silently gets truncated to `6.022` -- the exponent is dropped with no error, no warning, and
      a wrong resulting value. This is the immediate trigger for the bug above: the model appears
      to get stuck trying to expand the unrepresentable exponent into decimal digits, and that
      runaway digit generation bleeds into the *next* parameter instead of stopping cleanly.
      **Fixed**: `FloatState` gained three new stages (`POST_SCIENTIFIC_E_TOKEN`,
      `POST_SCIENTIFIC_SIGN`, `POST_SCIENTIFIC_EXP`) that branch off `POST_FLOAT_POINT` on an
      `e`/`E` token, requiring an explicit `+`/`-` then one or more exponent digits. Verified
      against 7 new fixtures in `data/input/float_tests/` covering positive/negative
      exponents, explicit/implicit signs, and the non-scientific case -- all pass. Full detail in
      `claude/reports/report_6_20260824-153702.md`. A related but separate gap surfaced during
      verification: numbers with no decimal point at all (`PRE_FLOAT_POINT` never allows
      termination without first emitting a `.`) can still overflow on very long digit runs --
      not yet its own issue, noted in `report_6`.
- [ ] **The `<\|im_end\|>`/`<\|im_start\|>` prompt-injection guard (`src/call_me_maybe.py`) is an
      exact, case-sensitive substring check and is trivially bypassed.** Re-running the original
      successful injection attack with the casing changed to uppercase (`<\|IM_END\|>`), with extra
      internal whitespace (`<\| im_end \|>`), or swapped for a different real special token entirely
      (`<\|endoftext\|>`, never checked for) bypasses the guard in all three cases -- `"<|im_end|>"
      in prompt` doesn't match any of them. In the specific cases tested, the underlying model was
      not actually fooled by any of the three variants (it correctly answered the genuine request
      instead of executing the injected instruction), but that's incidental to this particular
      model's behavior on these particular inputs, not something the guard itself guarantees --
      the original exact-match attack did succeed before the guard was added, so a variant using
      the *real* token sequence (which the guard does catch) remains the actual risk. The guard
      provides much narrower coverage than its intent suggests.

## Notes

The first two items compound: dropping the exponent isn't just a values-truncation bug on its
own, it appears to be *what causes* the runaway generation that produces the `Infinity` result on
the following parameter. Fixing the exponent-dropping (either by rejecting scientific notation
outright with a clean `GenerationError`, or by extending `FloatState`'s grammar to support it) would
likely also prevent this specific overflow trigger, but the underlying gap -- nothing validates
that a generated number is finite before serialization -- would remain a real issue on its own for
any sufficiently long run of digits, scientific notation involved or not.
