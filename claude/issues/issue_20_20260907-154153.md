# Dead code: two unused pydantic models, an uncalled adapter method, and an unreachable except clause

None of this is harmful and none of it breaks a rule. It is grouped into one issue because a
single cleanup pass removes all of it, and because every item is a question a reviewer can ask
that has no good answer beyond "that is left over".

## 1. `Functions` and `Prompts` models are never referenced

`src/models/context.py` defines two models that nothing imports or instantiates:

```python
class Functions(BaseModel):
    model_config = ConfigDict(extra="forbid")
    functions: List[Function]


class Prompts(BaseModel):
    model_config = ConfigDict(extra="forbid")
    prompts: List[PromptEntry]
```

```
$ grep -rn "\bFunctions\b\|\bPrompts\b" src/ | grep -v "^src/models/context.py"
(no output)
```

They are also not exported from `src/models/__init__.py`. `Context` already holds
`functions: List[Function]` and `prompts: List[PromptEntry]` directly, which is what
`Context.model_validate` actually validates against, so these two are a superseded intermediate
step.

## 2. `Adapter.parse` / `JSONAdapter.parse` has no callers

```
$ grep -rn "\.parse(" src/ | grep -v parser
(no output)
```

Input decoding goes through `pydantic_core.from_json` in `CallMeMaybe.__get_context`, not through
the adapter -- the README's "Design decisions" section explains why, and the reasoning is sound.
Only `serialize` is used, by `__write_output`.

Two options, and the choice depends on issue #12: that issue proposes decoding generated values
with `json.loads`, which is exactly what `JSONAdapter.parse` wraps. So either delete `parse` from
both the ABC and the implementation, or **give it its caller** by routing issue #12's string
decode through it. The second is more coherent -- the adapter exists to own the JSON boundary, and
right now it owns only half of it.

`DeserializationException` is used only by `parse`, so its fate follows.

## 3. Unreachable `except DeserializationException`

`Model.__load_string_end_sequences` catches an exception the block cannot raise:

```python
# src/model/model.py:32-41
try:
    with open(self.get_path_to_vocab_file()) as vocab_file:
        vocab_dict: Dict[str, int] = json.loads(vocab_file.read())
    ...
except OSError as e:
    raise FatalGenerationError(f"Failed to open vocab file: {e}")
except DeserializationException as e:
    raise FatalGenerationError(f"Failed to parse vocab file: {e}")
```

The block calls `json.loads` directly, which raises `json.JSONDecodeError`, never
`DeserializationException` -- that is only raised by `JSONAdapter.parse`, which is not used here.
A malformed vocab file therefore falls through to the generic `except Exception` below and is
reported as "An unknown error occured while loading string end sequences" rather than as a parse
failure.

Either catch `json.JSONDecodeError`, or route the load through `JSONAdapter.parse` so the
existing clause becomes correct -- which pairs naturally with option 2 above.

Same pattern in `__get_context`, whose `except (OSError, json.JSONDecodeError)` includes a
`JSONDecodeError` that block cannot raise either (covered in issue #19).

## 4. Unused constant in the test runner

```python
# tests/__main__.py
STDOUT = ROOT / "outputs" / "last_run_stdout.log"
```

Never read, and it points at an `outputs/` directory that does not exist (the runner writes to
`tests/stdout/`). Not submitted, so cosmetic only.
