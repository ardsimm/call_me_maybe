# A merged vocab token can smuggle a stray character past `IntState`'s digit check

Found while picking new prompts to add to `data/input/function_calling_tests.json`, re-testing
the adversarial `"-42-4"` / `"-42-"` boundary prompts from an earlier debugging session against
`fn_int_len`. Both now fail (gracefully, but fail) after the minus-sign fix, via a mechanism
distinct from anything found before.

## Repro

```
uv run python -m src --input <(echo '[{"prompt": "What is the length of \"-42-4\""}]')
```

Token trace for the `n` parameter (`src/generate/__generator_impl.py`'s debug logging):

```
Generated: -
Generated: 4
Generated: 2
Generated: -",
Error: Invalid value for parameter of type int: -42-
```

The fourth generated token is a single vocab token whose surface text is literally `-",` (hyphen +
quote + comma, three characters, one token). Since this token *does* contain an unescaped `"`, it
is a member of `Model.string_end_sequences` and therefore legal to pick from `IntState`'s `DATA`
stage (`_stage_allowed_tokens[DATA] = digits_tokens + string_end_sequences`,
`src/state/__int_state.py`) -- but nothing about that check verifies that the *rest* of the token's
text (the leading `-`) is itself a valid digit. It gets spliced straight into the value, producing
`-42-` instead of `-42`. `int("-42-")` then raises `ValueError`, caught by `generate_parameters`
and converted to `GenerationError` -- a clean per-prompt failure, not a crash (the batching/error
handling holds up correctly here), but the extraction itself is wrong.

## Root cause

`Model.__load_string_end_sequences` (`src/model/model.py`) classifies a vocab token as an
end-of-string sequence purely by regex on that token's own text:

```python
if re.search(r'(?<!\\)"', key):
    self.__string_end_sequences.append(token_id)
```

This says nothing about whether the token consists *only* of closing punctuation. A token that
happens to bundle extra content alongside a quote (here, a stray `-` immediately before it) still
qualifies, and `IntState`'s `DATA` stage has no way to reject it without also rejecting every
legitimate end-of-string token -- there's no mechanism to accept "the terminator part" of a token
while rejecting "the leading garbage part" of that same token.

## Checklist

- [x] `IntState` accepts a merged `<non-digit><quote>...` token from `DATA`, corrupting the
      generated integer with trailing garbage instead of cleanly ending the value. Confirmed via
      `"What is the length of \"-42-4\""` -> generated `-42-` -> `int()` `ValueError` ->
      `GenerationError` (no crash, but wrong/failed extraction). `"-42-"` is expected to hit the
      same path (not separately confirmed).
      **Practically resolved, not structurally fixed.** `FloatState` gained a real structural fix
      for the leading-minus case specifically (a new `POST_MINUS_TOKEN` stage whose allowed tokens
      are digits only, so a merged token can never be picked immediately after a leading `-`).
      `IntState`'s own code is otherwise byte-for-byte unchanged. An extensive re-test --
      `data/input/trailing_minus/` (17 prompts: leading/no-leading minus, single/double/trailing
      minus, embedded mid-string minus, short and long digit runs, int and float, with and without
      decimals) -- came back clean across the board, including `"-123456789-"` (a much longer digit
      run than the original repro) and `"-4-2"` (embedded mid-string). So the practical risk is
      resolved under the current prompt templates, but there's still no explicit code-level filter
      preventing a merged token from being selected inside `DATA`/`POST_FLOAT_POINT` -- the
      robustness comes from the model's own behavior under today's prompts, the same "defense via
      model behavior, not a hard guarantee" pattern already documented for the injection guard
      (`issue_3` #3). Worth revisiting if this ever resurfaces after a template or model change.
- [ ] `FloatState`'s `POST_FLOAT_POINT` stage has the identical shape
      (`digits_tokens + Model.string_end_sequences` as `_stage_allowed_tokens`,
      `src/state/__float_state.py`) and is likely affected by the same class of merged token, though
      this was not reproduced directly -- worth checking against a similar adversarial float prompt
      (e.g. `"-42.0-4"`). Re-tested as part of the `trailing_minus` suite above and also came back
      clean, same caveat as `IntState` applies (no explicit filter, just not currently triggered).
- [ ] Root cause is shared with any future numeric state built the same way: `string_end_sequences`
      membership is computed per-token with no constraint that the token contains *only* closing
      punctuation, so any vocab token that bundles a terminator with unrelated leading characters
      can slip content past a numeric grammar's digit-only intent.
