# Exception-handling gaps: several failure paths bypass intended error handling

Full detail in `claude/reports/report_2_20260823-212921.md`. Found while writing docstrings'
`Raises` sections, which required tracing every call path's exceptions end to end rather than just
what each function raises itself.

Two of these (#1-#3 below) reproduce the exact "whole batch silently loses its output" shape as the
`TokenizerFactory` arity mismatch and `parameter.valie` typo bugs fixed earlier this session — just
triggered by different inputs.

## Checklist

*Status re-checked 2026-08-24 against the current codebase -- a lot has changed since this was
written, several items are now partially or fully resolved as side effects of unrelated fixes.*

- [~] **`Context.__init__` exceptions escape `run()`'s catch** -- **partially fixed.**
      `Context.__init__` (`src/models/context.py`) now wraps `Function`/`Parameter` construction
      in `try: ... except ValueError as err: raise ParsingError(...)`. Since
      `pydantic.ValidationError` is itself a `ValueError` subclass (confirmed:
      `issubclass(pydantic.ValidationError, ValueError) == True`), this now also catches the
      bad-`ParameterType` case *and* the empty-name/description case, both converted cleanly to
      `ParsingError` and caught by `run()`. Still open: `TypeError` from `value["type"]` if a
      parameter entry isn't a dict (only `ValueError` is caught, not `TypeError`), and
      `OSError`/`json.JSONDecodeError` from the two unguarded `open()`/`json.loads()` calls at the
      top of `__init__` -- both still escape `run()`'s catch uncaught.
- [~] **All-or-nothing batching** -- **exposure reduced, structurally still open.**
      `__process_prompts` still only catches `GenerationError` per prompt, same shape as before.
      But the two concrete triggers this issue originally cited (the boolean `ValueError` and
      numeric parsing `ValueError`) are now both handled *locally inside* `__process_prompt`
      (`__strip_number` + a local `try/except ValueError` with a `42`/`42.0` fallback for
      int/float; the bool branch no longer raises at all, see item 4). So the practical likelihood
      of hitting this is much lower than when written, but the structural gap -- anything else
      unexpected raised from `generate_name`/`generate_parameters`/`GeneratorFactory.get_instance`
      still takes down the whole batch -- remains.
- [ ] **`main()` always exits 0, even on crash** -- still open, unchanged.
      `src/__main__.py`'s `except Exception` prints a traceback but never calls `sys.exit(1)`.
- [x] **Boolean branch raises `ValueError` instead of `GenerationError`** -- **resolved, by a
      different fix than expected.** The bool-coercion branch in `call_me_maybe.py` no longer
      raises anything on an invalid value at all -- it prints a message and falls back to
      `parsed_parameter = ""` locally, the same graceful-degradation pattern now used for
      int/float. Nothing escapes to `__process_prompts` anymore for this case.
- [ ] **`JSONAdapter.serialize`/`.parse` catch the wrong exception type** -- still open, unchanged.
      `serialize` still catches `json.JSONDecodeError` instead of the `TypeError` that
      `json.dumps` actually raises; `SerializationException` still can never fire via `serialize`.
- [ ] **`Arguments.validate_model` catches the wrong exception type** -- still open, unchanged.
- [ ] **`StateFactory.get_instance`'s `TRIE_STATE` branch is broken** -- still open, unchanged.
      `StateType` still has no `TRIE_STATE` member.
- [ ] **`SystemExit` from argparse bypasses the app's own error messaging** -- still open,
      unchanged (minor).

## Suggested priority

1 -> 2 -> 3 together close the actual proven failure mode (a bad input silently zeroing out a
whole run's output) and should go first -- 1 is now partly done, 2's remaining exposure is lower
than before but not zero, 3 is the one that would make either of them loud instead of silent if
they ever do trigger. 5 and 6 are correctness/clarity fixes for exception types that don't match
their `except` clauses -- lower urgency since something further out already catches the fallout
today. 7 is a cheap, defensive one-liner worth doing opportunistically; 8 is minor and arguably
correct as-is for `--help`.
