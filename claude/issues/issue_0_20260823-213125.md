# Exception-handling gaps: several failure paths bypass intended error handling

Full detail in `claude/reports/report_2_20260823-212921.md`. Found while writing docstrings'
`Raises` sections, which required tracing every call path's exceptions end to end rather than just
what each function raises itself.

Two of these (#1-#3 below) reproduce the exact "whole batch silently loses its output" shape as the
`TokenizerFactory` arity mismatch and `parameter.valie` typo bugs fixed earlier this session — just
triggered by different inputs.

## Checklist

- [ ] **`Context.__init__` exceptions escape `run()`'s catch** (confirmed reachable) --
      `ValueError`/`TypeError`/`pydantic.ValidationError`/`OSError`/`json.JSONDecodeError` from
      `src/models/context.py:__init__` are not caught by `run()`'s
      `except (ParsingValidationError, ParsingError)` in `src/call_me_maybe.py`. Includes the
      already-known bad-`ParameterType` crash.
- [ ] **All-or-nothing batching** (confirmed reachable) -- `__process_prompts` only catches
      `GenerationError` per prompt; results are written once at the end, so any other exception
      mid-batch discards every already-generated result. `src/call_me_maybe.py`.
- [ ] **`main()` always exits 0, even on crash** (confirmed reachable) -- `src/__main__.py`'s
      `except Exception` prints a traceback but never calls `sys.exit(1)`; masks the two issues
      above as a "successful" 0 exit with zero output.
- [ ] **Boolean branch raises `ValueError` instead of `GenerationError`** (latent) --
      `src/call_me_maybe.py`'s bool-coercion `else` branch; not caught by `__process_prompts`'
      `except GenerationError`. Unreachable today (trie grammar guarantees `"true"`/`"false"`
      only), but a trap if that ever changes.
- [ ] **`JSONAdapter.serialize`/`.parse` catch the wrong exception type** (latent, masked) --
      `src/adapter/__json_adapter.py` catches `json.JSONDecodeError`, but `json.dumps` raises
      `TypeError` on non-serializable values; `SerializationException` can never actually fire via
      `serialize`.
- [ ] **`Arguments.validate_model` catches the wrong exception type** (latent, masked) --
      `src/models/arguments.py`: `json_adapter.parse()` already converts `JSONDecodeError` into
      `DeserializationException` before `validate_model` sees it, so its own
      `except json.JSONDecodeError` is dead code; the real `DeserializationException` (and any
      `OSError` from the unguarded `open()` calls) propagates unwrapped, not as
      `pydantic.ValidationError`, since pydantic only auto-wraps `ValueError`/`TypeError`/
      `AssertionError` raised in a validator. Currently masked by `ArgumentParser.parse`'s own
      blanket `except Exception`.
- [ ] **`StateFactory.get_instance`'s `TRIE_STATE` branch is broken** (latent) --
      `src/state/state_factory.py` checks `type == StateType.TRIE_STATE`, but `StateType`
      (`src/state/state_type.py`) has no such member -- raises `AttributeError` instead of the
      intended `ValueError`. Never called this way today.
- [ ] **`SystemExit` from argparse bypasses the app's own error messaging** (minor) --
      `src/parsing/__argument_parser.py`: `--help`/an unrecognized flag calls `sys.exit()`
      directly, which isn't an `Exception` subclass, so it skips the `"Parsing failed: ..."`
      convention used everywhere else. Arguably correct for `--help`.

## Suggested priority

1 -> 2 -> 3 together close the actual proven failure mode (a bad input silently zeroing out a
whole run's output) and should go first. 5 and 6 are correctness/clarity fixes for exception types
that don't match their `except` clauses -- lower urgency since something further out already
catches the fallout today. 4 and 7 are cheap, defensive one-liners worth doing opportunistically.
