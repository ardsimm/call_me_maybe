# `extra="forbid"` plus a closed type enum rejects the whole functions file for ordinary schema
shapes

Every model in `src/models/context.py` sets `model_config = ConfigDict(extra="forbid")`, and
`ParameterType` is a closed enum of exactly four spellings:

```python
class ParameterType(StrEnum):
    INT = "int"
    FLOAT = "number"
    BOOL = "boolean"
    STRING = "string"
```

Because `Context.model_validate` validates both files in one call, **any** unexpected key or
unrecognised type string anywhere in `functions_definition.json` rejects the entire file, and
the run produces no output for any prompt.

## Measured behaviour

Each of these was run against an otherwise-valid prompts file. All produce
`Parsing failed: Failed to parse JSON input: 1 validation error for Context` and an empty run:

| Reviewer's functions file contains | Result |
|---|---|
| `"a": {"type": "string", "description": "the name"}` | whole file rejected |
| `"times": {"type": "integer"}` instead of `"int"` | whole file rejected |
| `"required": ["name"]` on a function | whole file rejected |
| `"returns": {"type": "array"}` | whole file rejected |
| a UTF-8 BOM at the start of either file | whole file rejected |

Fixtures for all of these are now in `tests/test_cases/malformed_inputs/` and wired into the
`make test` robustness set.

## Why this is a risk rather than a bug

The subject warns twice that the inputs are not fixed:

> "The given input files **may change** during the peer review. Do not hardcode solutions based
> on the provided examples." (V.4.2)
>
> "Argument types must match the function definition (**number, string, boolean, etc.**)" (V.4.2)

That "etc." is doing real work, and none of the rejected shapes above are exotic:

- A `description` on a parameter is the standard shape in OpenAI's function-calling schema,
  Anthropic's tool schema, and JSON Schema itself. It is arguably the single most likely thing a
  reviewer adds when writing their own file.
- `"integer"` is the JSON Schema spelling of what this project calls `"int"`. Note the project
  already accepts `"number"` for floats, i.e. it is *already* using JSON Schema vocabulary --
  just inconsistently, since JSON Schema's integer type is `"integer"`, not `"int"`.
- `"required": [...]` is how JSON Schema marks mandatory arguments.

To be clear about what is **not** wrong here: the failure is entirely graceful. Clear message,
exit code 0, no traceback, no partial output file. The error-handling requirements (IV.1, V.5)
are met in every case. The risk is purely that a reviewer supplies a perfectly reasonable file
and watches the program produce nothing at all -- which reads as broken even though it is behaving
exactly as designed.

## Fix

Three small changes, all in `src/models/context.py` plus one line in `__get_context`.

**1. Tolerate descriptive extra keys.** Switch `Parameter` and `Function` from `extra="forbid"`
to `extra="ignore"`. Keeping `extra="forbid"` on `PromptEntry` is fine if the strictness there is
wanted -- a stray key in the prompts file is more likely a mistake than a schema dialect.

**2. Accept common type aliases.** A `mode="before"` validator keeps the enum closed internally
while widening what the file may say:

```python
_TYPE_ALIASES = {
    "integer": "int", "float": "number", "double": "number",
    "bool": "boolean", "str": "string", "text": "string",
}

class Parameter(BaseModel):
    @field_validator("type", mode="before")
    @classmethod
    def _normalize_type(cls, v: object) -> object:
        return _TYPE_ALIASES.get(v, v) if isinstance(v, str) else v
```

Apply the same to `Returns`.

**3. Absorb a BOM.** Open both input files with `encoding="utf-8-sig"` in
`CallMeMaybe.__get_context` -- a one-word change that makes a file saved by Notepad or exported
from Excel work.

## The alternative: keep the strictness, but say so

Rejecting unknown keys is a legitimate design stance, and the README's "Design decisions" section
already argues for pydantic-owned validation persuasively. If the strictness is kept deliberately,
the README should state the accepted schema **exactly** -- the four type spellings, no extra keys
-- rather than presenting `extra="forbid"` as pure upside with no trade-off, which is how it reads
today. A reviewer who knows the constraint up front will write a conforming file; one who does not
will conclude the program is broken.

- [ ] If widening: add a `mode="before"` field validator mapping `integer`/`float`/`double`/
