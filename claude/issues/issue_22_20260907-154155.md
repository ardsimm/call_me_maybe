# `data/input/` duplicates `tests/test_cases/`, and the README's usage examples point at the copy that may not ship

Five scenario directories exist twice, byte-identical:

```
$ diff -rq data/input/multi_param_types tests/test_cases/multi_param_types
(no differences)
```

Same for `ambiguous_and_adversarial`, `edge_values`, `extreme_edge_cases`, `new_functions` and
the nested `extreme_edge_cases/injection_guard_robustness`, plus a full copy of
`malformed_inputs/`.

## The contradiction

The README's "Testing strategy" section says the tests are not shipped:

> *The following tests will not be included in the submit for this project but can be recovered
> from [the github repository](https://github.com/ardsimm/call_me_maybe)*

But its "Example usage" section -- the part a reviewer actually runs -- points into `tests/`:

```sh
uv run python -m src \
  --functions_definition tests/test_cases/multi_param_types/functions_definition.json \
  --input tests/test_cases/multi_param_types/function_calling_tests.json \
  --output data/output/multi_param_types.json
```

So if `tests/` really is stripped before submission, the README's headline usage example fails
with a missing-file error on the reviewer's machine. The `make test` and `./run_tests` examples
in the same section break too.

## Which way to resolve it

**Keep `tests/` in the submission** (recommended). The subject says tests are "not submitted or
graded" (IV.3), which means *not graded* -- it does not forbid including them, and Chapter VIII's
list ends with "any additional files needed to run your solution". A working `make test` that
grades 68 prompts and writes a report is a strong thing to have during a defense, and the subject's
Bonus Part explicitly lists "Comprehensive test suite". Then:

- delete the `data/input/` duplicates, keeping only `functions_definition.json`,
  `function_calling_tests.json` and `function_calling_showcase.json` -- which is what the subject
  means by "`data/input/` directory with test files (for demonstration)";
- remove the "will not be included in the submit" line from the README.

**Or strip `tests/`**, in which case the `data/input/` copies become the canonical fixtures and
every README example must be repointed at them -- including the `make test` and `./run_tests`
examples, which would then have nothing to run.

The current state is the worst of both: the fixtures are maintained in two places (so they can
drift apart silently), and the documentation describes a third arrangement that matches neither.

## Note on `make clean`

```make
clean:
	find . -type d -name output -exec rm -rf {} +
```

This matches **any** directory named `output` anywhere in the tree -- currently `data/output/`,
`tests/output/` and `tests/test_cases/malformed_inputs/output/`. All three are generated and
git-ignored, so nothing is lost today, and the subject's `clean` rule is meant to remove exactly
this kind of artifact. Worth anchoring the paths anyway (`rm -rf data/output tests/output`) so the
glob cannot reach somewhere unintended later. Note it also conflicts with the project's own
`CLAUDE.md` guideline "Do not delete `data/output/` files before running a test".

## Checklist

- [ ] Decide whether `tests/` ships with the submission (recommended: yes).
- [ ] If yes: delete the duplicated scenario directories under `data/input/`, keeping the default
      pair plus `function_calling_showcase.json`.
- [ ] If yes: remove the "will not be included in the submit" line from the README's "Testing
      strategy" section.
- [ ] If no: repoint every `tests/test_cases/...` path in the README's "Example usage" at the
      `data/input/` copies, and drop the `make test` / `./run_tests` examples.
- [ ] Either way, ensure each fixture has exactly one home so the two copies cannot drift.
- [ ] Anchor `make clean`'s `find ... -name output` to explicit paths.
