# `IntState` lets the model repeat `-` indefinitely instead of forcing a digit

Found while reviewing a fix to `CallMeMaybe.__strip_number` (`src/call_me_maybe.py`) that had
briefly introduced an infinite loop on inputs with no digit at all. That specific bug is fixed
now, but tracing through it surfaced a real structural gap in `IntState` itself: the grammar has no
mechanism preventing the model from picking `-` over and over, with no digit ever required to
follow.

## The gap

`src/state/__int_state.py`:

```python
self._stage_allowed_tokens = {
    IntStateStage.INITIAL: minus_token + digits_tokens,
    IntStateStage.DATA: (digits_tokens + string_end_sequences),
    IntStateStage.TERMINAL: None,
}

self._stage_transition_tokens = {
    IntStateStage.INITIAL: digits_tokens,
    IntStateStage.DATA: string_end_sequences,
}
```

At `INITIAL`, both `-` and any digit are legal (`_stage_allowed_tokens`), but only a digit actually
advances the state machine to `DATA` (`_stage_transition_tokens[INITIAL] = digits_tokens`, which
does not include `minus_token`). Picking `-` is a legal move that leaves the state sitting in
`INITIAL` -- the model can, in principle, pick `-` again immediately afterward, and again after
that, indefinitely. Nothing in the grammar ever forces a digit; the only thing that can eventually
stop this is `GeneratorImpl.TOKEN_GEN_LIMIT` (currently 250) running out, at which point the
generated value is some run of `-` characters up to that length, with no digit anywhere in it.

`FloatState` had this exact same shape at one point and was given a real fix for it: a dedicated
`POST_MINUS_TOKEN` stage whose allowed tokens are digits *only* (no `string_end_sequences`, no
second `-`), so picking `-` there forces the very next token to be a digit or generation cannot
proceed further in a way that ever reaches a valid terminator. `IntState` never received the
equivalent stage -- it still allows `-` to be re-picked from `INITIAL` with no such forcing
function.

## Current impact (contained, but wasteful)

With `__strip_number`'s loop-termination fix now in place (`while ... and s_len > 0`), a
`-`-only value no longer hangs the process: `__strip_number` correctly reduces it to `""`,
`int("")` raises `ValueError`, and `__process_prompt`'s `except ValueError` catches it and
substitutes the `42` placeholder -- the same graceful degradation path as any other malformed
numeric value. So today this is not a crash or a hang. But it is:

- **Wasteful**: if the model ever does get stuck oscillating on `-`, it burns up to
  `TOKEN_GEN_LIMIT` (250) generation steps before the cap forces a stop, for a value that was
  never going anywhere -- real latency cost for zero information gained.
- **A near-miss repeat of the exact bug class this session already found and fixed once** (the
  original `__strip_number` infinite loop). The only reason it's not a hang *right now* is that a
  completely separate piece of code (`__strip_number`'s guard) happens to catch the degenerate
  output after the fact. If `__strip_number` or its guard is ever touched again without this
  context in mind, the underlying grammar gap that produces `-`-only values is still there to
  reintroduce the same class of problem.

## Checklist

- [x] `IntState`'s `INITIAL` stage allows `-` to be re-picked indefinitely with no digit ever
      required to follow, unlike `FloatState`'s `POST_MINUS_TOKEN` stage which was added
      specifically to close this gap for floats. Give `IntState` the equivalent: a stage entered
      immediately after a leading `-` whose allowed tokens are digits only, forcing progress
      before a value can ever terminate.
      **Fixed**: `IntState` gained a `POST_MINUS` stage (`src/state/__int_state.py`) whose allowed
      tokens are digits only -- no `string_end_sequences`, no second `-` -- via a custom
      `_advance_stage` override that routes `INITIAL` to either `POST_MINUS` (on `-`) or
      `POST_DIGIT` (on a digit) directly, mirroring `FloatState`'s shape. Structurally closes the
      root cause: `-` can no longer be picked more than once in a row, or ever be the final
      character of a value. Verified: all 17 `data/input/trailing_minus/` cases still pass
      byte-for-byte, and a full 5-scenario regression run (`claude/test_cases/`) is clean with
      every int-typed parameter (`seat_number`, `attendees`, `age`, `quantity`, etc.) still
      correct. One harmless leftover: `_stage_transition_tokens[INITIAL]` is now unused, since the
      custom `_advance_stage` override handles `INITIAL` itself without consulting it.
- [x] Once fixed, re-verify `data/input/trailing_minus/`'s leading-minus cases (`-42`, `--42`,
      etc.) still behave correctly, since this changes `IntState`'s stage graph the same way the
      `FloatState` fix did. Confirmed above.
