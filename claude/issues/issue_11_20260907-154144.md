# String values longer than 67 tokens are silently truncated by `TOKEN_GEN_LIMIT`

`GeneratorImpl.TOKEN_GEN_LIMIT = 67` caps every generated value, strings included:

```python
# src/generate/__generator_impl.py:153
while token is not None and token_count < self.TOKEN_GEN_LIMIT:
```

The README describes it as "a hard cap of 67 tokens per value as a safety net", and as a guard
against a state that never signals completion that is exactly right. The problem is that it
applies to `StringState` too, where it is not a safety net but an active data-loss bug.

## Measured

The `extreme_edge_cases` long-note fixture loses its tail. Measuring the truncated output back
through the tokenizer:

```
truncated value: 374 chars, 68 tokens
GeneratorImpl.TOKEN_GEN_LIMIT = 67
```

The cut lands exactly on the cap. Reproduced independently in the new
`tests/test_cases/string_round_trip/` scenario, whose last prompt asks for a ~390-character
value and gets back 366 characters ending mid-word ("right u").

**The truncation is completely silent.** Nothing is printed, no exception is raised, and the
output is valid JSON containing a plausible-looking but wrong value -- the worst failure shape,
because it cannot be distinguished from a correct answer by looking at the output file.

## Why strings do not need the cap

The cap exists because `IntState` and `FloatState` can genuinely run away: a model that keeps
picking digit tokens has no reason to stop, and `POST_SCIENTIFIC_EXP` in particular can generate
digits until the float overflows (which is how the `Infinity` bug documented in the README's
"Challenges faced" arose). A bound there is load-bearing.

`StringState` is different. It terminates when the model picks any token from
`Model.string_end_sequences`, which is what closing the JSON string looks like -- and since the
prompt template ends mid-string with `name:"`, the model reaches that naturally. The cap is not
what makes string generation terminate; it just decides how much gets thrown away when a
legitimate value happens to be long.

67 tokens is roughly 350-400 characters of English. A note, a review, an email body, a SQL query
or a file path list can all exceed that trivially -- and `fn_store_note`, `fn_send_email` and
`fn_run_sql` are all functions already in this project's own fixtures.

## Fix

Make the limit a property of the `State` rather than a constant on the generator:

```python
# src/state/state.py
class State:
    token_limit: int = 67          # numeric states inherit this

# src/state/__string_state.py
class StringState(State):
    token_limit = 512
```

and read `constrainer.state.token_limit` in `__get_completion` instead of
`self.TOKEN_GEN_LIMIT`.

Independently of the limit chosen, **make the truncation loud**. Any value that ends because the
cap was hit, rather than because the state signalled completion, should say so:

```python
if token_count >= limit:
    print(f"Warning: value truncated at the {limit}-token generation cap")
```

Silent wrong answers are worse than loud short ones, and this also makes the condition visible
in the `tests/stdout/` logs the test runner already captures.

Mind the interaction with speed (issue #15): a higher cap on strings raises the worst-case
number of forward passes per parameter. It only costs anything on values that are actually long,
but it is worth re-running `make test` for the timing as well as the accuracy.

- [ ] Read `constrainer.state.token_limit` in `GeneratorImpl.__get_completion`

- [ ] Print a warning whenever a completion ends because the cap was hit rather than because the
